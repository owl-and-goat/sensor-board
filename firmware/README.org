#+title: firmware

* build and flash

over swd with probe-rs, st-link plugged into the jtag port:

#+begin_src sh
  cargo run --release                        # flash, reset, stay attached (ctrl-c to leave)
  cargo flash --release --chip stm32wb55cg   # flash, reset, exit
#+end_src

** without a probe: usb dfu

for a board that is not on the swd cable, the rom bootloader takes the image
over usb. ask the running firmware for its bootloader first; with several
boards in the bootloader pick one with =dfu-util -p <usb path>= (=lsusb -t=).

#+begin_src sh
  sensor-board-cli bootloader --board <serial>
  elf=target/thumbv7em-none-eabihf/release/sensor-board-firmware
  $(rustc --print sysroot)/lib/rustlib/*/bin/llvm-objcopy -O binary $elf app.bin
  dfu-util -d 0483:df11 -a 0 -s 0x08000000:leave -D app.bin
#+end_src

* talking to a board: sensor-board-cli

the firmware is a usb device with one vendor interface, which carries
[[https://github.com/jamesmunns/postcard-rpc][postcard-rpc]] messages. the endpoints and every type in them are defined in
=../protocol=; the firmware serves them (=src/rpc.rs=) and
=../cli= calls them. a board's usb serial number is its chip's
unique id, and =--board= takes any unambiguous start of it.

#+begin_src sh
  cd ../cli
  cargo run -- list                        # every board: firmware build, network status
  cargo run -- network init                # all attached boards onto one thread network
  cargo run -- network dataset --board 4b  # that network's dataset, hex (holds the network key)
  cargo run -- network leave --board 4d
  cargo run -- coprocessor status --board 4d           # what cpu2 has installed and runs
  cargo run -- coprocessor install <image> --board 4d  # see "a new board" below
  cargo run -- coprocessor uninstall --board 4d        # remove the wireless stack
  cargo run -- bootloader --board 4d       # reboot into the rom bootloader
#+end_src

=network init= puts every attached board on one network, each joining in
turn and waited for until it has attached. which network: the one saved by
an earlier run, in =~/.local/state/sensor-board/dataset= (=--dataset-path=
names another file); with nothing saved, the one of the first board that has
one; failing that a new one (random key, pan id and channel). whichever it
is, it is saved, so a board plugged in on its own later joins the same
network. =--force-reinit= makes a new network regardless and moves the
attached boards to it. the saved file holds the network key.

the host makes the dataset; a board is only ever told to join one. a board
keeps its dataset in flash and rejoins at every power-up, until =network
leave=.

* getting into the bootloader

only needed for dfu; probe-rs does not care. any of these puts the chip in
usb dfu mode (=lsusb= shows =0483:df11=):

- short the two pads of jp1 (boot0) while plugging in usb. hardware only;
  works no matter what is in flash. take the coin cell out first: vbus and the
  cell share a net.
- =sensor-board-cli bootloader=, while the app runs.
- a panic, hard fault or watchdog reset in the app.

* cpu2: fus, the thread stack, and openthread

cpu2 (the cortex-m0+ radio core) runs st's signed firmware: fus (the
firmware upgrade service) and, once installed, the thread ftd stack.

** a new board

a chip comes blank, with an old fus and no wireless stack. from the top of
the repository, with the board on usb and nothing else:

#+begin_src sh
  just new-board          # this firmware over dfu, then fus and the thread stack; under a minute
  just cli network init   # onto the network saved by an earlier run
#+end_src

=just new-board= fetches st's two images, checks them against known hashes,
and then does this:

#+begin_src sh
  dfu-util -d 0483:df11 -a 0 -s 0x08000000:leave -D sensor-board-firmware.bin
  sensor-board-cli coprocessor install stm32wb5x_FUS_fw.bin          # fus 1.2.0 -> 2.2.0, a few seconds
  sensor-board-cli coprocessor install stm32wb5x_Thread_FTD_fw.bin   # about half a minute
#+end_src

without =--board=, =coprocessor install= takes the only attached board whose
coprocessor is running fus, which is the new one. it reads from the image
what it is, and leaves alone a board that already has that version.

fus only installs while it is the one running, so a board that has a stack
takes =coprocessor uninstall= first.

done this way on 2026-10-04 for the third and fourth boards. the first two
got their stacks in september from the text console of the bring-up firmware
(commit 9caa670).

** result (2026-09-16, two boards side by side on one hub)

a leader (rloc16 0xd400) and b child (0xd401) on channel 14, pan 0x5f11.
ping a to b 5/5 with 21 to 69 ms rtt, b to a 5/5 with 21 to 23 ms. a's
neighbor table: b at rssi -18 dbm, link margin 82 db, lqi 3. antenna,
balun and stack all work; range and tx power are untested.
