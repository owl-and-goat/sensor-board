#+title: firmware

* build and flash

a board needs two images: the bootloader from =../bootloader=, at the start
of flash, and this firmware after it. the bootloader only swaps in a firmware
update (see below) and starts the firmware. from the top of the repository:

#+begin_src sh
  just flash                  # both, through the st-link on the jtag port
  just update                 # the firmware, over usb, through the running firmware
  just update-all             # the same for every attached board, one after the other
  just push                   # the firmware, to every board on the network, through the attached one
  just dfu-flash              # both, over usb, through the rom bootloader
  just dfu-flash-all          # the same for every attached board, one after the other
#+end_src

with several boards attached, =just update=, =just push= and =just dfu-flash=
take =--board <serial>=. to flash only the firmware through the probe and
watch the board's log (the bootloader has to be on the board already):

#+begin_src sh
  cargo run --release         # flash, reset, stay attached (ctrl-c to leave)
#+end_src

** firmware updates

=just update= runs =sensor-board-cli firmware update <image>= with the image
that =just firmware-image= builds. the board writes the image to its staging
area in flash, verifies it, and restarts. its bootloader then swaps the two
firmwares, which takes about ten seconds. the new firmware first runs on
trial. once the board is back on its network (or has no network to join),
the update is confirmed. if the board restarts before that, or is not back
within five minutes, the bootloader restores the old firmware. =firmware
status= shows which build is running and the state of the update.

=just push= runs =firmware push <image>=, which updates every board on the
network without plugging any of them in. the attached board receives the
image over usb and offers it to the others every ten seconds. a board that
runs another build fetches the image from the attached board in small
chunks, verifies it, and restarts into it in the same way, including the
trial. the command follows the boards' reports, which show the build each
board runs. it updates the attached board last, once every board it has
heard from runs the image. a board whose trial of a build failed does not
fetch that build again.

during a push, the command shows a summary line with the number of boards
that run the image, and below it a progress bar for each board that is
fetching. the bars are based on the chunks that the boards request from the
attached board:

#+begin_example
  ⠙ 1 of 3 other boards run build 1791154812 (2m)
  4B0041000350475532303120 ███████████████░░░░░░░░░░░░░  56%    1.85 KiB/s  eta 48s
  a board                  ███░░░░░░░░░░░░░░░░░░░░░░░░░  12%    1.71 KiB/s  eta  2m
  4D0021000350475532303120 ████████████████████████████ 100%  restarting
#+end_example

a bar shows the board's serial number once the board has sent its id.
firmware from before 2026-10-04 does not send it, so such a board is shown
as "a board". a board that has the whole image keeps its bar for half a
minute while it verifies the image, restarts and swaps, and is listed as
=updated= at its next report. the bars are only drawn on a terminal (and not
if =TERM= is =dumb=), and only if the attached board's firmware can report
progress (run =just update= first if it cannot).

all boards fetch at the same time, even when they relay for each other (see
=TODO.org=). a board can only be updated this way once it runs a firmware
that supports it, so its first such firmware has to come over usb.

a board stays on its network through all of this: its stored configuration
is in a separate page that neither firmware slot covers.

** without the firmware: usb dfu

=just dfu-flash= asks the running firmware to enter the rom bootloader and
then runs the command below. the command also works on a board that entered
the rom bootloader another way (see "getting into the bootloader"). with
several boards in the rom bootloader, select one with =dfu-util -p <usb
path>= (=lsusb -t= shows the paths).

#+begin_src sh
  dfu-util -d 0483:df11 -a 0 -s 0x08000000:leave -D target/sensor-board-flash.bin
#+end_src

the image is the bootloader, padded with blank flash up to 0x08007000,
followed by the firmware (=just firmware-image=, then the bootloader's part
of =_flash-image= in the =Justfile=).

* talking to a board: sensor-board-cli

the firmware is a usb device with one vendor interface, which carries
[[https://github.com/jamesmunns/postcard-rpc][postcard-rpc]] messages. =../protocol= defines the endpoints and all their
types. the firmware serves them (=src/rpc.rs=) and =../cli= calls them. a
board's usb serial number is its chip's unique id, and =--board= takes any
unambiguous prefix of it.

#+begin_src sh
  cd ../cli
  cargo run -- list                        # every board: firmware build, network status
  cargo run -- network init                # put all attached boards on one thread network
  cargo run -- network dataset --board 4b  # that network's dataset, hex (holds the network key)
  cargo run -- network neighbors --board 4b  # that board's direct neighbors and their link quality
  cargo run -- network routers --board 4b  # every router, and the board's route to it
  cargo run -- network leave --board 4d
  cargo run -- coprocessor status --board 4d           # what cpu2 has installed and is running
  cargo run -- coprocessor install <image> --board 4d  # see "a new board" below
  cargo run -- coprocessor uninstall --board 4d        # remove the wireless stack
  cargo run -- bootloader --board 4d       # reboot into the rom bootloader
  cargo run -- firmware status --board 4d  # the running build, and the state of an update
  cargo run -- firmware update <image> --board 4d  # see "firmware updates" above
  cargo run -- firmware push <image> --board 4d    # update every board on the network
  cargo run -- network addresses --board 4b  # that board's ipv6 addresses
  cargo run -- reports watch               # print the boards' sensor reports as they arrive
  cargo run -- metrics show --board 4d     # the board's current prometheus metrics
  cargo run -- config show --board 4d      # the board's configuration
  cargo run -- config set --board 4d --sensor temperature=30s  # see "board configuration" below
#+end_src

=network init= puts every attached board on one network. the boards join one
at a time, and the command waits for each to attach. it chooses the network
in this order: the one saved by an earlier run, in
=~/.local/state/sensor-board/dataset= (=--dataset-path= selects another
file); if nothing is saved, the network of the first board that has one;
otherwise a new network (random key, pan id and channel). the chosen network
is saved, so that a board plugged in on its own later joins the same one.
=--force-reinit= always creates a new network and moves the attached boards
to it. the saved file contains the network key.

the host creates the dataset, and a board is only ever told to join one. a
board keeps its dataset in flash and rejoins at every power-up, until
=network leave=.

** sensor reports

every board multicasts a report with its sensor readings to its network
every ten seconds. =reports watch= prints the reports that one attached
board receives, including that board's own, for as long as the command runs.
the board has to stay attached: if it goes away (unplugged, reflashed), the
command waits for it to come back. any board can do this. a board only
understands reports from firmware with the same report layout, and ignores
the rest. =firmware push= also uses these reports, to learn which build each
board runs.

** metrics

a board exports its metrics to prometheus itself, over its thread network
and a border router. how it exports them depends on the power mode in its
configuration (see below):

- =aux=: the board serves a scrape endpoint at =/metrics= on tcp port 9469.
  it handles one scrape at a time.
- =battery=: the board pushes to the pushgateway in its configuration after
  every sensor read, as job =sensor_board= with its serial number as the
  instance. after a failed push it waits a minute before the next one.

a board without a configuration does neither.

the metrics are the readings of the sensors enabled in the configuration,
each read at its own interval, plus counters for scrapes and pushes. every
metric has a =board= label with the board's serial number. =metrics show=
prints the current metrics over usb.

to scrape a board, prometheus needs an address that is reachable from
outside the thread network. =network addresses= lists it as =routable=. a
board gets one once a border router advertises a prefix.

#+begin_src yaml
  scrape_configs:
    - job_name: sensor-board
      static_configs:
        - targets: ["[fd12:3456:789a:1:4c51:2d3d:c69c:4af6]:9469"]
#+end_src

a pushgateway is set as an ipv6 address and a port. the border router has to
be able to route from the board to that address:

#+begin_src sh
  cargo run -- config set --power-mode battery --pushgateway '[fd12:3456::1]:9091'
#+end_src

tested on a board on 2026-10-10: metrics over usb, switching between the two
modes when the configuration changes, and pushes to addresses where nothing
answers. not tested yet, because there was no border router or second board
to test with: a scrape, and a push that succeeds.

** board configuration

a board stores a configuration in flash, next to its network's dataset. it
holds the board's number, its power mode, and for each sensor either a poll
interval or that the sensor is off. =config show= prints it. =config set=
changes the settings it is given and keeps the rest. the power mode also
selects how the board exports its metrics (see "metrics" above):

#+begin_src sh
  cargo run -- config set --id 3 --power-mode aux    # a board's first configuration needs these two
  cargo run -- config set --sensor temperature=30s --sensor color=off
  cargo run -- config show
#+end_src

with =--remote <serial>=, both commands apply to a board that is not
attached. the attached board asks it over their network, and gives up after
six seconds. =--remote= takes the board's full serial number, as =reports
watch= prints it.

#+begin_src sh
  cargo run -- config set --remote 4D0021000350475532303120 --sensor temperature=30s
#+end_src

a firmware that changes the layout of the configuration (by adding a sensor,
for example) cannot read a configuration that the previous firmware stored.
the board then has no configuration until it is set again. two boards whose
firmwares have different layouts do not answer each other's requests either.

so far only the metrics use the configuration: the power mode, the
pushgateway, and the intervals of the sensors that have a driver. the
board's number is not used yet. sensor reports are sent every ten seconds
regardless, and a board on battery is still a full router.

* getting into the bootloader

only needed for dfu; probe-rs does not need it. any of these puts the chip in
usb dfu mode (=lsusb= shows =0483:df11=):

- short the two pads of jp1 (boot0) while plugging in usb. this is hardware
  only, so it works whatever is in flash. take the coin cell out first: vbus
  and the cell share a net.
- =sensor-board-cli bootloader=, while the firmware is running.
- three boots in a row that end in a panic, a hard fault or a watchdog reset.
  a single failure only restarts the firmware.

* cpu2: fus, the thread stack, and openthread

cpu2 (the cortex-m0+ radio core) runs st's signed firmware: fus (the
firmware upgrade service) and, once installed, the thread ftd stack.

** a new board

a new chip is blank, with an old fus and no wireless stack. from the top of
the repository, with only the new board on usb:

#+begin_src sh
  just new-board          # bootloader and firmware over dfu, then fus and the thread stack; under a minute
  just cli network init   # join the network saved by an earlier run
#+end_src

=just new-board= fetches st's two images, verifies them against known hashes,
and then runs these commands:

#+begin_src sh
  dfu-util -d 0483:df11 -a 0 -s 0x08000000:leave -D sensor-board-flash.bin
  sensor-board-cli coprocessor install stm32wb5x_FUS_fw.bin          # fus 1.2.0 -> 2.2.0, a few seconds
  sensor-board-cli coprocessor install stm32wb5x_Thread_FTD_fw.bin   # about half a minute
#+end_src

without =--board=, =coprocessor install= selects the only attached board
whose coprocessor is running fus, which is the new one. it reads the kind
and version from the image, and skips a board that already has that version.

fus can only install while fus itself is running, so a board that has a
stack needs =coprocessor uninstall= first.

the third and fourth boards were set up this way on 2026-10-04. the first
two got their stacks in september from the text console of the bring-up
firmware (commit 9caa670).

** result (2026-09-16, two boards side by side on one hub)

a leader (rloc16 0xd400) and b child (0xd401) on channel 14, pan 0x5f11.
ping a to b 5/5 with 21 to 69 ms rtt, b to a 5/5 with 21 to 23 ms. a's
neighbor table: b at rssi -18 dbm, link margin 82 db, lqi 3. antenna,
balun and stack all work; range and tx power are untested.
