# sensor-board

The board is built on an STM32WB55CG, which has two cores. CPU1 runs the
firmware in this repository. CPU2, the radio coprocessor, runs ST's signed
firmware: FUS (the firmware upgrade service) and the Thread stack it installs.

- `firmware/`: the Embassy firmware for CPU1.
- `protocol/`: the postcard-rpc endpoints and every type in them. The firmware
  serves them (`firmware/src/rpc.rs`) and the CLI calls them.
- `cli/`: `sensor-board-cli`, the host tool that talks to boards over USB.

How to flash a board, use the CLI and set up a new board is in
`firmware/README.org`. What follows is what neither that nor the code makes
obvious.

## Conventions

How Aspen wants the code written:

- Separation of concerns. A module owns one thing and gives the rest of the
  firmware a typed way to it. The pattern for anything that runs: a
  `Builder { peripherals }.init()` hands back a `Task` to run and a `Handle`
  to ask things of it (see `coprocessor`, `thread`, `usb`).
- No module-level mutable state. What a task and its handles share is made
  in one place, the `init` that returns them as a tuple, and each of them
  holds a reference to it. The exception is the few words that have to
  survive a reset, which are `.uninit` statics in `dfu.rs` and
  `coprocessor/fus.rs`.
- Every embassy task is in `firmware/src/main.rs`. The task function there
  only calls into its module, so that `main.rs` shows everything that runs.
  This is also why no RPC handler is of the spawning kind.
- Well-defined data types, not loose strings or raw codes. Whatever crosses
  USB is a Rust type in `protocol`, used by both the firmware and the CLI.
- Keep it simple, and keep out code that only exists to try out the hardware.
- Calls into CPU2 are wrapped in `firmware/src/thread/ot.rs`, each with a
  `SAFETY` comment that says what the call expects.

Format with `cargo fmt`, one crate at a time. `firmware/src/thread/ffi.rs` is
generated by `firmware/tools/gen-thread-bindings.sh` and is not in rustfmt's
style: leave it as generated.

## Tools

`shell.nix` provides `just`, `dfu-util` and `probe-rs`, and direnv loads it in
an interactive shell. A shell without direnv may lack them (on Aspen's machine
it has `probe-rs` but neither `just` nor `dfu-util`):
run recipes from the top of the repository as `nix-shell --run 'just <recipe>'`.

## probe-rs

`cargo run --release` in `firmware/` flashes over SWD and then stays attached,
printing the log; it does not return by itself. `cargo flash --release --chip
STM32WB55CG` flashes, resets and exits. Both erase only the pages the image
covers, so the stored configuration in the last application page and
everything CPU2 owns are left alone.

Keep `--no-catch-reset` in the runner in `firmware/.cargo/config.toml`. The
firmware resets itself on purpose (a bootloader request, a panic, a launch by
the ROM bootloader). With probe-rs's default reset catch each of those ends
the run with "Firmware exited unexpectedly" and leaves the core halted at the
reset vector, off USB, until the next probe-rs command attaches and lets it go.

The SWD connection drops when FUS resets the chip: `probe-rs attach` does not
survive a coprocessor install.

## Logs and panics

Logging is defmt over RTT, read through the probe. `DEFMT_LOG` in
`firmware/.cargo/config.toml` sets the level that is compiled in; without it
defmt keeps errors only. To watch a board that is already running, without
flashing or resetting it, from `firmware/`:

```sh
probe-rs attach --chip STM32WB55CG --no-catch-reset target/thumbv7em-none-eabihf/release/sensor-board-firmware
```

A panic goes to panic-probe, which logs the message over defmt and raises a
HardFault. What happens next depends on the probe (all three measured on
2026-10-03):

- Under `cargo run`: probe-rs stops on the fault, prints a backtrace and
  exits, leaving the core halted.
- No probe-rs session since power-up: `fault.rs` reboots into the ROM
  bootloader, about a second later.
- A probe-rs session ran earlier and has exited: its hard-fault catch stays
  armed until a power cycle. The core sits halted until the watchdog resets
  it, 32 s later, and only then reaches the bootloader.

## The ROM bootloader

`firmware/src/dfu.rs` gets there with a magic word in an `.uninit` RAM word
and a system reset: the first statement of `main` checks the word and jumps to
system memory (0x1FFF0000) before any clock or peripheral is touched. A
watchdog reset takes the same jump, so a hang ends in the bootloader too. The
hardware path, JP1 shorted at plug-in, is independent of all this.

Do not:

- Use `dfu-util` alt settings 1 (option bytes) or 2 (OTP). Alt 0 only.
- Set read protection (RDP) or write option bytes over DFU.
- Let the application image grow past the address CPU2's stack is installed
  at. `firmware/memory.x` caps it at 256 KB, the last 4 KB of which is the
  stored configuration.

## Clocks and the watchdog

Set in `configure_clocks` in `firmware/src/main.rs`, starting from embassy's
`WPAN_DEFAULT`:

- The system clock is the 32 MHz crystal (HSE), directly.
- The PLL runs only to give USB its 48 MHz, out of reach of what CPU2 does to
  HSI48.
- HSI16 stays on although CPU1 does not use it: the RF core clocks itself from
  it.
- The 32.768 kHz crystal (LSE) runs the RTC and the RF wakeup clock.

The independent watchdog is started by the `watchdog` task. Whatever is
written to `IWDG_PR` on this chip, it reads back as 6 (/256) once the update
flag clears, while `IWDG_RLR` takes any value; this is not in the ES0394
errata sheet. The task asks the driver for 32 s, and a watchdog reset was
measured to come about 32 s after the core stopped (2026-10-03). The IWDG
keeps running in Stop mode unless the `IWDG_STOP` option bit is cleared, so a
low-power firmware must feed it or freeze it.

## CPU2: FUS and the Thread stack

ST's images are in STM32CubeWB, under
`Projects/STM32WB_Copro_Wireless_Binaries/STM32WB5x/`. The firmware, and the
bindings in `firmware/src/thread/ffi.rs`, are written against V1.24.0.

`coprocessor install` sends an image to the firmware, which writes it where
FUS looks for one: on the page boundary that leaves it ending just below the
secure flash area. That is also where ST's release notes put each image
(0x080EE000 for FUS and 0x0808C000 for the Thread stack, on a 1 MB part). FUS
then installs it, resetting the chip a few times, and starts an installed
stack without being asked. FUS only installs while it is the one running.

A join stores the dataset in the last 4 KB page of the application's flash
(`firmware/src/persistent_config.rs`, 0x0803F000), because CPU2 forgets its
own settings when it restarts. At power-up a board with a stored dataset hands
it back to the stack and rejoins by itself.

Things learned the hard way:

- The ROM bootloader boots CPU2 for its own FUS commands, and a CPU1 reset
  does not restart CPU2. After a DFU `:leave` the firmware finds CPU2 holding
  the bootloader's mailbox pointers, so it wipes that marker and takes a real
  system reset first (`reset_if_launched_by_bootloader`).
- FUS answers its commands into whichever mailbox CPU2 booted with. Before the
  fix above, an upgrade looked hung when it had actually run.
- A wireless stack switches the 48 MHz clock off unless CPU1 holds hardware
  semaphore 5 (AN5289). The firmware takes it before C2BOOT and keeps it.
- With HSI16 off, `SHCI_C2_THREAD_Init` never answers.
- The Thread stack uses SRAM1 above 0x20024000: CPU1's RAM is capped at
  144 KB.
- CPU2 needs the traces queue initialised, and something has to drain its
  traces and acknowledge its OpenThread notifications.
- In stack v1.24 the OpenThread CLI runs on CPU1, not CPU2, and everything
  goes through the OT command channel (3). The CLI channel (5) still has to be
  received from and acknowledged: with nothing doing that,
  `SHCI_C2_THREAD_Init` never answers.
- FUS resets CPU1 during an upgrade. The watchdog's jump to the bootloader is
  disabled while a FUS operation is marked as in progress (`fus_busy`).
- FUS can report itself idle, with no error, while an install is still ahead
  of it: for 14 s in the middle of installing the Thread stack. The firmware
  therefore remembers across resets what FUS was set to do, and takes the
  change in what CPU2 reports having as the end of it.
- Given a file that is no image, or the FUS version it already is, FUS reports
  neither an error nor a reset: it stays idle. Only a minute of that is taken
  as "nothing was installed".
- After installing a stack, FUS starts it by itself on its last reset.
- CPU2 is inside an OpenThread callback until its notification is
  acknowledged, and what the notification points at is only valid until then:
  the message of a received UDP datagram has to be read out first.
  `ThreadNotifRx::receive_with` in embassy-stm32-wpan is for that, and the
  calls made inside it are blocked on (`thread/ot.rs`). CPU2 answers calls
  while a notification is outstanding. ST's own code never acknowledges one
  while a call is waiting for its answer, and neither does the Thread service.
- A UDP datagram sent to a multicast address comes back to the sender's own
  socket if `mMulticastLoop` is set. That is how a collecting board hears its
  own report.

## Sensor reports

`firmware/src/report.rs` sends a `protocol::Report` to every board
(`ff03::1`, UDP port 61620) every ten seconds. A board that the host has told
to collect binds that port and passes on what arrives as the `ReportReceived`
topic. A new sensor goes into `protocol::Readings`, `Task::readings` in
`report.rs`, and `describe` and `Metrics` in `cli/src/reports.rs`. Changing
`Report` changes the key its datagrams start with, so boards with the old
layout and boards with the new one do not hear each other.
