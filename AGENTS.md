# sensor-board

The board is built on an STM32WB55CG, which has two cores. CPU1 runs the
firmware in this repository. CPU2, the radio coprocessor, runs ST's signed
firmware: FUS (the firmware upgrade service) and the Thread stack that FUS
installs.

- `bootloader/`: the first code to run on CPU1. It swaps a staged firmware
  update in, or rolls one back, and then starts the firmware.
- `firmware/`: the Embassy firmware for CPU1.
- `protocol/`: the postcard-rpc endpoints and all their types. The firmware
  serves them (`firmware/src/rpc.rs`) and the CLI calls them.
- `cli/`: `sensor-board-cli`, the host tool that talks to boards over USB.

`firmware/README.org` explains how to flash a board, use the CLI and set up a
new board. This file covers what is not obvious from the README or the code.

## Conventions

How Aspen wants the code written:

- Separation of concerns. Each module owns one thing and exposes a typed
  interface to the rest of the firmware. Anything that runs follows one
  pattern: `Builder { peripherals }.init()` returns a `Task` to run and a
  `Handle` for sending it requests (see `coprocessor`, `thread`, `usb`).
- No module-level mutable state. The state shared by a task and its handles
  is created in one place, the `init` function that returns them, and each of
  them holds a reference to it. The only exceptions are the few words that
  have to survive a reset: the `.uninit` statics in `dfu.rs` and
  `coprocessor/fus.rs`.
- Every embassy task is defined in `firmware/src/main.rs`. Each task function
  only calls into its module, so `main.rs` shows everything that runs. For
  the same reason, no RPC handler spawns a task.
- Well-defined data types instead of loose strings or raw codes. Everything
  that crosses USB is a Rust type in `protocol`, shared by the firmware and
  the CLI.
- Keep it simple. Do not keep code that only exists to try out the hardware.
- Calls into CPU2 are wrapped in `firmware/src/thread/ot.rs`. Each wrapper
  has a `SAFETY` comment that states what the call expects.
- Write comments, docs and commit messages plainly: short declarative
  sentences, the standard technical terms, and imperative commit subjects
  that name the change ("Add command to read the router table").

Format with `cargo fmt`, one crate at a time. `firmware/src/thread/ffi.rs` is
generated by `firmware/tools/gen-thread-bindings.sh`. The committed file is
rustfmt-formatted, so run `cargo fmt` on the firmware crate after
regenerating it.

## Tools

`shell.nix` provides `just`, `dfu-util` and `probe-rs`, and direnv loads it in
interactive shells. A shell without direnv may lack them: on Aspen's machine
such a shell has `probe-rs`, but neither `just` nor `dfu-util`. In that case,
run recipes from the top of the repository with
`nix-shell --run 'just <recipe>'`.

## probe-rs

`just flash` writes the bootloader and the firmware over SWD as one image,
resets the board and exits. `cargo run --release` in `firmware/` writes only
the firmware, so the bootloader has to be on the board already. It then stays
attached and prints the log, and does not return by itself. Both commands
erase only the pages that the image covers, so they leave the stored
configuration and everything CPU2 owns untouched.

`cargo run` does not change the bootloader's state page. If the firmware it
replaces was an update still on trial, the bootloader treats the reset as a
failed trial and swaps the older firmware over the one that was just flashed.
`just flash` avoids this, because its image blanks the state page.

Keep `--no-catch-reset` in the runner in `firmware/.cargo/config.toml`. The
firmware resets itself on purpose: for a bootloader request, after a panic,
and after a launch by the ROM bootloader. With probe-rs's default reset
catch, each of those resets ends the run with "Firmware exited unexpectedly"
and leaves the core halted at the reset vector, off USB, until the next
probe-rs command attaches and resumes it.

The SWD connection drops when FUS resets the chip, so `probe-rs attach` does
not survive a coprocessor install.

## Logs and panics

Logging uses defmt over RTT and is read through the probe. `DEFMT_LOG` in
`firmware/.cargo/config.toml` sets the log level that is compiled in. Without
it, defmt only keeps errors. To watch a running board without flashing or
resetting it, run this from `firmware/`:

```sh
probe-rs attach --chip STM32WB55CG --no-catch-reset target/thumbv7em-none-eabihf/release/sensor-board-firmware
```

panic-probe handles a panic: it logs the message over defmt and raises a
HardFault. What happens next depends on the probe. The first and the last
case were measured on 2026-10-03, with the firmware of that day:

- Under `cargo run`: probe-rs stops on the fault, prints a backtrace and
  exits, leaving the core halted.
- No probe-rs session since power-up: `fault.rs` counts a failed boot and
  restarts the board. This has not been measured since the handler was
  changed from jumping to the ROM bootloader.
- A probe-rs session ran earlier and has exited: its hard-fault catch stays
  armed until a power cycle. The core stays halted until the watchdog resets
  it, 32 s later.

A watchdog reset also counts as a failed boot. A restart after a failure
rolls back a firmware update that is on trial. After three failed boots in a
row the board enters the ROM bootloader (`MAX_FAILED_BOOTS` in `dfu.rs`), so
that a firmware that cannot stay up can still be replaced over USB. One
minute of running clears the count. The failed-boot counting has not been
tested on hardware yet.

## The ROM bootloader

`firmware/src/dfu.rs` enters the ROM bootloader by writing a magic value to
an `.uninit` RAM word and resetting the system. The first statement of the
firmware's `main` checks that word and jumps to system memory (0x1FFF0000)
before any clock or peripheral is configured. Our own bootloader has already
run at that point, which is why it does not call `embassy_stm32::init` and
only uses the flash controller. The firmware makes the same jump after
several failed boots in a row (see above). The hardware method, shorting JP1
while plugging the board in, is independent of all this.

Do not:

- Use `dfu-util` alt settings 1 (option bytes) or 2 (OTP). Use alt 0 only.
- Set read protection (RDP) or write option bytes over DFU.
- Change the regions in `firmware/memory.x` without changing
  `bootloader/memory.x` to match. No CPU1 region may reach the address where
  CPU2's stack is installed (0x0808C000).

## Firmware updates

The flash below CPU2's stack has this layout (`memory.x` in `bootloader/` and
`firmware/`):

| From       | Size  | What                                                |
|------------|-------|-----------------------------------------------------|
| 0x08000000 | 24 K  | bootloader (embassy-boot, about 3.5 K of it used)   |
| 0x08006000 | 4 K   | the bootloader's state page                         |
| 0x08007000 | 224 K | the firmware                                        |
| 0x0803F000 | 4 K   | stored configuration (`persistent_config.rs`)       |
| 0x08040000 | 228 K | the staging area for an update                      |

`firmware/src/update.rs` writes an image to the staging area, checks its
SHA-256, and marks the state page. At the next reset the bootloader swaps the
staging area with the firmware. The update then runs on trial (see the module
doc). If the board resets before the update is confirmed, the bootloader
swaps the old firmware back. Tested on a board on 2026-10-04: the swap, a
trial being confirmed, the rollback after a reset during the trial, and an
update from the rolled-back state. Not tested: the five-minute timeout of a
trial.

An image reaches the staging area from the host over USB, or from another
board over the network (`UpdateMessage` in `protocol`, on UDP port 61621,
which every board listens on). Once the host tells a board with a staged
image to offer it, that board multicasts an offer every ten seconds. A board
that runs another build requests the image from the offering board 192 bytes
at a time, stages it, and restarts into it. A board whose trial of a build
failed finds that build in its staging area afterwards, and does not fetch
it again.

The offering board records the offset that each board last requested. That
is the only progress information `firmware push` has (`GetOfferProgress`). A
fetching board also sends its ID (`UpdateMessage::Fetching`) when it starts
and at every offer it receives, so that its progress bar can show its serial
number. The bars use indicatif, which draws nothing unless stderr is a
terminal and `TERM` is not `dumb`.

The encoding of `UpdateMessage` is frozen, and tests in `protocol` pin its
bytes, because a board on an old firmware has to understand the offer of the
firmware that replaces it. Add new messages at the end of the enum: a
firmware that does not know a message ignores it. Tested on boards on
2026-10-04: a push to the whole network, with boards fetching from the
attached one.

Things learned the hard way:

- A page that a flash loader (probe-rs's or the ROM bootloader's) has filled
  with 0xff reads as erased but cannot be programmed. Every write to it fails
  with PROGERR, even an all-zero one, until the page is erased again. Writing
  the whole flash image leaves the state page in that condition, so
  `update.rs` erases the page before marking it.
- While a stack runs on CPU2, flash must only be written through `RadioFlash`
  (`radio_flash.rs`). The Thread service, the update service and the
  configuration service share it behind a mutex inside the coprocessor task.
- An image contains the sixteen bytes that mark it as this firmware
  (`BuildMarker`) twice: once in the marker itself, and once in the constant
  that the firmware searches for markers with. The marker includes a check
  value so that only the real marker matches.
- The bootloader has to fit in 24 K in every profile. An unoptimized build
  does not fit, so its dev profile is size-optimized like its release
  profile.
- Boards and the CLI often run different builds. Add new endpoints instead of
  changing the request or response type of an existing one. If only the
  response type changes, old firmware still runs the handler, and the CLI
  times out waiting for the new type.

## Clocks and the watchdog

`configure_clocks` in `firmware/src/main.rs` sets up the clocks, starting
from embassy's `WPAN_DEFAULT`:

- The system clock is the 32 MHz crystal (HSE), used directly.
- The PLL runs only to give USB its 48 MHz. USB cannot use HSI48, because
  CPU2 can switch that off.
- PLLSAI1 gives the microphone's SAI 8.192 MHz. Both PLLs divide the crystal
  by 5 first (the divider is shared), the only way to reach an audio rate
  from 32 MHz.
- HSI16 stays on although CPU1 does not use it, because the RF core is
  clocked from it.
- The 32.768 kHz crystal (LSE) drives the RTC and the RF wakeup clock.

The `watchdog` task starts the independent watchdog. On this chip, `IWDG_PR`
reads back as 6 (/256) once the update flag clears, whatever value was
written to it, while `IWDG_RLR` accepts any value. The ES0394 errata sheet
does not mention this. The task requests 32 s from the driver, and a watchdog
reset was measured about 32 s after the core stopped (2026-10-03). The IWDG
keeps running in Stop mode unless the `IWDG_STOP` option bit is cleared, so a
low-power firmware has to feed it or freeze it.

## CPU2: FUS and the Thread stack

ST's images are in STM32CubeWB, under
`Projects/STM32WB_Copro_Wireless_Binaries/STM32WB5x/`. The firmware and the
bindings in `firmware/src/thread/ffi.rs` are written against V1.24.0.

`coprocessor install` sends an image to the firmware, which writes it where
FUS looks for one: on the page boundary that makes the image end just below
the secure flash area. ST's release notes give the same address for each
image (0x080EE000 for FUS and 0x0808C000 for the Thread stack, on a 1 MB
part). FUS then installs the image, resetting the chip a few times, and
starts an installed stack by itself. FUS can only install an image while FUS
itself is running, not while a stack is.

A join stores the dataset in the stored-configuration page, between the
firmware and the staging area (`firmware/src/persistent_config.rs`,
0x0803F000), because CPU2 loses its own settings when it restarts. At
power-up, a board with a stored dataset passes it to the stack and rejoins
by itself.

Things learned the hard way:

- The ROM bootloader boots CPU2 for its own FUS commands, and a CPU1 reset
  does not restart CPU2. After a DFU `:leave`, the firmware therefore finds
  CPU2 still using the bootloader's mailbox pointers. It clears the
  bootloader's marker and does a full system reset first
  (`reset_if_launched_by_bootloader`).
- FUS sends its command responses to the mailbox that CPU2 booted with.
  Before the fix above, an upgrade looked hung although it had run.
- A wireless stack switches the 48 MHz clock off unless CPU1 holds hardware
  semaphore 5 (AN5289). The firmware takes the semaphore before C2BOOT and
  never releases it.
- With HSI16 off, `SHCI_C2_THREAD_Init` never returns.
- The Thread stack uses SRAM1 above 0x20024000, so CPU1's RAM is limited to
  144 KB.
- CPU2 needs the traces queue to be initialised. Something also has to drain
  its traces and acknowledge its OpenThread notifications.
- In stack v1.24 the OpenThread CLI runs on CPU1, not CPU2, and everything
  goes through the OT command channel (3). The CLI channel (5) still has to
  be received from and acknowledged. Otherwise `SHCI_C2_THREAD_Init` never
  returns.
- FUS resets CPU1 during an upgrade. While a FUS operation is marked as in
  progress (`fus_busy`), a watchdog reset does not count as a failed boot.
- FUS can report itself idle, with no error, while an install is still
  pending: it did so for 14 s in the middle of installing the Thread stack.
  The firmware therefore stores the pending FUS operation across resets, and
  treats a change in the versions that CPU2 reports as the end of the
  operation.
- If FUS is given a file that is not an image, or the FUS version that is
  already installed, it reports no error and does not reset. It just stays
  idle. The firmware concludes that nothing was installed only after a
  minute of that.
- After installing a stack, FUS starts it by itself on its last reset.
- CPU2 stays inside an OpenThread callback until its notification is
  acknowledged, and the data that the notification points to is only valid
  until then. So the message of a received UDP datagram has to be read before
  the acknowledgement. `ThreadNotifRx::receive_with` in embassy-stm32-wpan
  exists for this, and the calls made inside it block (`thread/ot.rs`). CPU2
  answers calls while a notification is outstanding. ST's own code never
  acknowledges a notification while a call is waiting for its answer, and
  neither does the Thread service.
- A UDP datagram sent to a multicast address is also delivered to the
  sender's own socket if `mMulticastLoop` is set. That is how a collecting
  board receives its own report.

## Sensor reports

`firmware/src/report.rs` multicasts a `protocol::Report` to every board
(`ff03::1`, UDP port 61620) every ten seconds. When the host tells a board to
collect, the board binds that port and forwards each report it receives to
the host as the `ReportReceived` topic.

- To add a sensor, add it to `protocol::Readings`, to `Task::readings` in
  `report.rs`, and to `describe` in `cli/src/reports.rs`.
- Changing `Report` changes the key that its datagrams start with. Boards
  with the old layout and boards with the new one then ignore each other's
  reports.
- `firmware push` uses the reports to learn which build each board runs. It
  does not wait for a board whose reports it does not receive.

## Metrics

`firmware/src/metrics.rs` polls the sensors that are enabled in the board's
configuration, each at its own interval, and exports the readings to
Prometheus. The power mode in the configuration selects how:

- `Aux`: the board serves a scrape endpoint at `/metrics` on TCP port 9469.
- `Battery`: the board pushes to its configured Pushgateway after every
  sensor read.

The metric types come from tinymetrics. `firmware/src/http.rs` implements
the HTTP: one request and one response per connection. To add a sensor, add
it to `SENSORS` and to the `match` in `Exporter::read`, and its metrics to
`Metrics`, all in `metrics.rs`.

TCP is OpenThread's own implementation, running on CPU2 (`otTcp*`, wrapped
in `thread/ot.rs`). The Thread service has one TCP endpoint, so the firmware
has one connection at a time. The rest of the firmware uses it through
`thread::Tcp`. CPU2 reports TCP events in callbacks, which arrive as
notifications.

Things learned about the TCP API:

- When a connection comes in, CPU2 asks in a callback whether to accept it,
  and into which endpoint. The return value is written where ST's handler
  writes it: over the notification's first argument, before the
  acknowledgement (`set_callback_result`). The endpoint is written through the
  pointer passed in the callback.
- `otTcpAbort` sends the disconnected callback from inside the call, and
  does not return until that notification is acknowledged. So
  `ot::tcp_abort` acknowledges notifications while the call is in progress.
  That is what `Ot_Cmd_TransferWithNotif` in ST's wrapper is for. So far no
  other call needs this.
- An endpoint that closed its side first stays in TIME-WAIT and accepts no
  connection until it is aborted. For that reason every exchange ends with
  `Tcp::close`.
- CPU2 reads sent data from the send buffer until the peer has acknowledged
  it. Nothing else can be sent before the send-done callback.
- If a type is missing from the bindings, regenerate them with
  `firmware/tools/gen-thread-bindings.sh`, then format them with the rest of
  the crate.
- `otIp6GetUnicastAddresses` returns a pointer into CPU2's own memory, which
  CPU1 can read. The firmware follows the list only while its pointers stay
  in RAM.

Tested on a board on 2026-10-10: initializing the endpoint and the listener,
listening, connections that are refused or never answered, aborting a
connection that is being opened, and switching between serving and pushing
when the configuration changes. Not tested yet, because there was no border
router: an incoming connection, and any data sent or received over a
connection.

## Board configuration

`protocol::BoardConfig` is stored in the stored-configuration page, after
the dataset (`firmware/src/persistent_config.rs`). The dataset record is at
the start of the page, where firmware from before 2026-10-07 wrote it and
still reads it. The configuration record is at offset 0x200: the postcard
encoding of `BoardConfig`, prefixed with a key derived from its layout.

`firmware/src/board_config.rs` serves the configuration. It runs inside the
coprocessor task because it writes flash. For a board that is not attached,
the attached board multicasts a request (`ConfigMessage`, UDP port 61622,
which every board listens on). The target board replies with the
configuration it then has stored, which after a `Set` shows whether it
stored the new one. The attached board resends the request every two
seconds, and gives up after six.

- Changing `BoardConfig` (a new sensor, a new field) changes both keys: the
  one in flash and the one that `ConfigMessage` starts with. A board then
  has no configuration until it is set again. Boards on different sides of
  the change ignore each other's requests instead of misreading them.
- Writing either record erases the page and writes both records again, with
  no other CPU1 code running in between (`RadioFlash::rewrite_page`). This
  matters because the Thread service reads the dataset from flash to tell
  whether the board has a network. A reset during the rewrite loses both
  records.
- When the dataset is written, a configuration record that the firmware
  cannot decode is copied over unchanged.
- Only the metrics use the configuration (`Monitor` in `board_config.rs`
  notifies them when it changes). The reports and Thread do not: a board on
  battery is a router like any other.
- A request goes to `ff03::1`, which does not reach a sleepy end device.

Tested on boards on 2026-10-07: setting a configuration over USB, and on
another board through the attached one. Both configurations survived a
firmware update, and the attached board's survived leaving its network and
joining it again.
