# sensor-board

The board is built on an STM32WB55CG, which has two cores. CPU1 runs the
firmware in this repository. CPU2, the radio coprocessor, runs ST's signed
firmware: FUS (the firmware upgrade service) and the Thread stack that FUS
installs.

- `bootloader/`: the first code to run on CPU1. It swaps a staged firmware
  update in, or rolls one back, and then starts the firmware.
- `firmware/`: the Embassy firmware for CPU1.
- `protocol/`: the postcard-rpc endpoints and all their types. The firmware
  serves them (`firmware/src/rpc.rs`) and the CLI calls them.
- `cli/`: `sensor-board-cli`, the host tool that talks to boards over USB.

`firmware/README.org` explains how to flash a board, use the CLI and set up a
new board. This file covers what is not obvious from the README or the code.

## Conventions

How Aspen wants the code written:

- Separation of concerns. Each module owns one thing and exposes a typed
  interface to the rest of the firmware. Anything that runs follows one
  pattern: `Builder { peripherals }.init()` returns a `Task` to run and a
  `Handle` for sending it requests (see `coprocessor`, `thread`, `usb`).
- No module-level mutable state. The state shared by a task and its handles
  is created in one place, the `init` function that returns them, and each of
  them holds a reference to it. The only exceptions are the few words that
  have to survive a reset: the `.uninit` statics in `dfu.rs` and
  `coprocessor/fus.rs`.
- Every embassy task is defined in `firmware/src/main.rs`. Each task function
  only calls into its module, so `main.rs` shows everything that runs. For
  the same reason, no RPC handler spawns a task.
- Well-defined data types instead of loose strings or raw codes. Everything
  that crosses USB is a Rust type in `protocol`, shared by the firmware and
  the CLI.
- Keep it simple. Do not keep code that only exists to try out the hardware.
- Calls into CPU2 are wrapped in `firmware/src/thread/ot.rs`. Each wrapper
  has a `SAFETY` comment that states what the call expects.
- Write comments, docs and commit messages the way you would say them to
  a colleague. Use the everyday words for things, even if the sentence gets
  longer: "the FDC2214 that's on the boards", not "that the boards carry";
  "minus the tank capacitor", not "less the tank capacitor"; "accurate to
  ±20 %", not "good to ±20 %". Write full sentences, not fragments. Use the
  standard technical terms, and imperative commit subjects that name the
  change ("Add command to read the router table").

Format with `cargo fmt`, one crate at a time. `firmware/src/thread/ffi.rs` is
generated by `firmware/tools/gen-thread-bindings.sh`. The committed file is
rustfmt-formatted, so run `cargo fmt` on the firmware crate after
regenerating it.

## Tools

`shell.nix` provides `just`, `dfu-util` and `probe-rs`, and direnv loads it in
interactive shells. A shell without direnv may lack them: on Aspen's machine
such a shell has `probe-rs`, but neither `just` nor `dfu-util`. In that case,
run recipes from the top of the repository with
`nix-shell --run 'just <recipe>'`.

`firmware/Cargo.toml` takes embassy-stm32 from the `wb55-stop` branch of
Aspen's fork of embassy (github.com/glittershark/embassy), which is the
released 0.6.0 with the fixes that make Stop mode work (see "Stop mode"
under "Boards on battery"). embassy-stm32-wpan comes from the `wb55-thread`
branch of the same fork. Each branch has a "NOT FOR UPSTREAM" commit that
replaces the path dependencies with released crates, so that the firmware
gets a single copy of each embassy crate. To change embassy-stm32, commit to
`wb55-stop`, push it, and update the `rev` in `firmware/Cargo.toml`.

## probe-rs

`just flash` writes the bootloader and the firmware over SWD as one image,
resets the board and exits. `cargo run --release` in `firmware/` writes only
the firmware, so the bootloader has to be on the board already. It then stays
attached and prints the log, and does not return by itself. Both commands
erase only the pages that the image covers, so they leave the stored
configuration and everything CPU2 owns untouched.

`cargo run` does not change the bootloader's state page. If the firmware it
replaces was an update still on trial, the bootloader treats the reset as a
failed trial and swaps the older firmware over the one that was just flashed.
`just flash` avoids this, because its image blanks the state page.

Keep `--no-catch-reset` in the runner in `firmware/.cargo/config.toml`. The
firmware resets itself on purpose: for a bootloader request, after a panic,
and after a launch by the ROM bootloader. With probe-rs's default reset
catch, each of those resets ends the run with "Firmware exited unexpectedly"
and leaves the core halted at the reset vector, off USB, until the next
probe-rs command attaches and resumes it.

The SWD connection drops when FUS resets the chip, so `probe-rs attach` does
not survive a coprocessor install.

## Logs and panics

Logging uses defmt over RTT and is read through the probe. `DEFMT_LOG` in
`firmware/.cargo/config.toml` sets the log level that is compiled in. Without
it, defmt only keeps errors. To watch a running board without flashing or
resetting it, run this from `firmware/`:

```sh
probe-rs attach --chip STM32WB55CG --no-catch-reset target/thumbv7em-none-eabihf/release/sensor-board-firmware
```

A board on battery that a probe has been attached to since it was powered up
does not enter Stop mode, so that its log can be read (see "Stop mode").

panic-probe handles a panic: it raises a HardFault. It does not log the
panic message, because its `print-defmt` feature is off. With the feature,
every panic message and source location stays in the image, which took 27 K
of flash (measured on 2026-10-11). To find a panic, read the backtrace that
probe-rs prints. That has not been tried on a board since the feature was
turned off.

What happens next depends on the probe. The first and the last case were
measured on 2026-10-03, with the firmware of that day:

- Under `cargo run`: probe-rs stops on the fault, prints a backtrace and
  exits, leaving the core halted.
- No probe-rs session since power-up: `fault.rs` counts a failed boot and
  restarts the board. This has not been measured since the handler was
  changed from jumping to the ROM bootloader.
- A probe-rs session ran earlier and has exited: its hard-fault catch stays
  armed until a power cycle. The core stays halted until the watchdog resets
  it, 32 s later.

A watchdog reset also counts as a failed boot. A restart after a failure
rolls back a firmware update that is on trial. After three failed boots in a
row the board enters the ROM bootloader (`MAX_FAILED_BOOTS` in `dfu.rs`), so
that a firmware that cannot stay up can still be replaced over USB. One
minute of running clears the count. The failed-boot counting has not been
tested on hardware yet.

## The ROM bootloader

`firmware/src/dfu.rs` enters the ROM bootloader by writing a magic value to
an `.uninit` RAM word and resetting the system. The first statement of the
firmware's `main` checks that word and jumps to system memory (0x1FFF0000)
before any clock or peripheral is configured. Our own bootloader has already
run at that point, which is why it does not call `embassy_stm32::init` and
only uses the flash controller. The firmware makes the same jump after
several failed boots in a row (see above). The hardware method, shorting JP1
while plugging the board in, is independent of all this.

Do not:

- Use `dfu-util` alt settings 1 (option bytes) or 2 (OTP). Use alt 0 only.
- Set read protection (RDP) or write option bytes over DFU.
- Change the regions in `firmware/memory.x` without changing
  `bootloader/memory.x` to match. No CPU1 region may reach the address where
  CPU2's stack is installed (0x0808C000).

## Firmware updates

The flash below CPU2's stack has this layout (`memory.x` in `bootloader/` and
`firmware/`):

| From       | Size  | What                                                |
|------------|-------|-----------------------------------------------------|
| 0x08000000 | 24 K  | bootloader (embassy-boot, about 3.5 K of it used)   |
| 0x08006000 | 4 K   | the bootloader's state page                         |
| 0x08007000 | 224 K | the firmware                                        |
| 0x0803F000 | 4 K   | stored configuration (`persistent_config.rs`)       |
| 0x08040000 | 228 K | the staging area for an update                      |

`firmware/src/update.rs` writes an image to the staging area, checks its
SHA-256, and marks the state page. At the next reset the bootloader swaps the
staging area with the firmware. The update then runs on trial (see the module
doc). If the board resets before the update is confirmed, the bootloader
swaps the old firmware back. Tested on a board on 2026-10-04: the swap, a
trial being confirmed, the rollback after a reset during the trial, and an
update from the rolled-back state. Not tested: the five-minute timeout of a
trial.

An image reaches the staging area from the host over USB, or from another
board over the network (`UpdateMessage` in `protocol`, on UDP port 61621,
which every board listens on). Once the host tells a board with a staged
image to offer it, that board multicasts an offer every ten seconds. A board
that runs another build requests the image from the offering board 192 bytes
at a time, stages it, and restarts into it. A board whose trial of a build
failed finds that build in its staging area afterwards, and does not fetch
it again.

The offering board records the offset that each board last requested. That
is the only progress information `firmware push` has (`GetOfferProgress`). A
fetching board also sends its ID (`UpdateMessage::Fetching`) when it starts
and at every offer it receives, so that its progress bar can show its serial
number. The bars use indicatif, which draws nothing unless stderr is a
terminal and `TERM` is not `dumb`.

Every board, whether it fetches or not, replies to every offer it receives
with its ID and the build it runs (`UpdateMessage::Running`). The offering
board keeps the last build of each board until the offer ends, and
`firmware push` reads them (`GetRunningBuilds`) to learn which build each
board runs. That includes boards on battery. A board starts to listen for
offers after its trial, so it replies with a new build only once it has
kept it. The push ends when every board it has heard from runs the image
and no board is still fetching. A board whose firmware predates `Running`
only shows up while it fetches.

`firmware push` can also offer an image without an attached board
(`push_through_border_router` in `cli/src/firmware.rs`). The CLI then does
what an offering board does. It sends the offer from UDP port 61621 to the
routable address of every device that the border router's REST API lists,
and of every board it finds over mDNS (see "Boards on battery"), and it
answers the chunk requests. A board sends its requests to port 61621
at the address the offer came from, which is why the CLI binds that port.

- The offers are unicast. A multicast to `ff03::1` does not leave or enter
  the Thread network.
- The offer goes to every listed device, not only to the boards that answer
  discovery. A board whose firmware predates discovery still has to get it.
- The CLI ignores the builds that the boards reply with
  (`UpdateMessage::Running`), so it does not know which build a board runs.
  It ends when no board has asked for anything for 30 s, and it reports the
  boards that fetched the image. It cannot tell a board that kept the image
  from one that rolled it back.
- A board gets a new address when it restarts into the image, so the device
  list from before the push no longer reaches it.

Tested on boards on 2026-10-11, with the two attached boards as the only
targets: both fetched from the CLI at the same time (about 2 KiB/s each, a
single board about 2.9 KiB/s), restarted and kept the image. Tested later
that day: a push with no board attached, to every device that the border
router lists and every board found over mDNS (see "Boards on battery").

The encoding of `UpdateMessage` is frozen, and tests in `protocol` pin its
bytes, because a board on an old firmware has to understand the offer of the
firmware that replaces it. Add new messages at the end of the enum: a
firmware that does not know a message ignores it. Tested on boards on
2026-10-04: a push to the whole network, with boards fetching from the
attached one.

Things learned the hard way:

- A page that a flash loader (probe-rs's or the ROM bootloader's) has filled
  with 0xff reads as erased but cannot be programmed. Every write to it fails
  with PROGERR, even an all-zero one, until the page is erased again. Writing
  the whole flash image leaves the state page in that condition, so
  `update.rs` erases the page before marking it.
- While a stack runs on CPU2, flash must only be written through `RadioFlash`
  (`radio_flash.rs`). The Thread service, the update service and the
  configuration service share it behind a mutex inside the coprocessor task.
- An image contains the sixteen bytes that mark it as this firmware
  (`BuildMarker`) twice: once in the marker itself, and once in the constant
  that the firmware searches for markers with. The marker includes a check
  value so that only the real marker matches.
- The bootloader has to fit in 24 K in every profile. An unoptimized build
  does not fit, so its dev profile is size-optimized like its release
  profile.
- Boards and the CLI often run different builds. Add new endpoints instead of
  changing the request or response type of an existing one. If only the
  response type changes, old firmware still runs the handler, and the CLI
  times out waiting for the new type.

## Clocks and the watchdog

`configure_clocks` in `firmware/src/main.rs` sets up the clocks, starting
from embassy's `WPAN_DEFAULT`:

- The system clock is the 32 MHz crystal (HSE), used directly.
- On aux power the PLL runs only to give USB its 48 MHz. USB cannot use
  HSI48, because CPU2 can switch that off. On battery the PLL is off, and
  the 48 MHz clock is HSI48, which CPU2 turns on while its random number
  generator needs it (`configure_clocks` takes the power mode).
- PLLSAI1 gives the microphone's SAI 8.192 MHz. Both PLLs divide the crystal
  by 5 first (the divider is shared), the only way to reach an audio rate
  from 32 MHz. The microphone driver turns PLLSAI1 on for a measurement and
  off after it.
- HSI16 stays on although CPU1 does not use it, because the RF core is
  clocked from it.
- The 32.768 kHz crystal (LSE) drives the RTC and the RF wakeup clock.
- MSI, which the chip starts on, is turned off (`stop_unused_clocks`).

The `watchdog` task starts the independent watchdog. On this chip, `IWDG_PR`
reads back as 6 (/256) once the update flag clears, whatever value was
written to it, while `IWDG_RLR` accepts any value. The ES0394 errata sheet
does not mention this. The task requests 32 s from the driver, and a watchdog
reset was measured about 32 s after the core stopped (2026-10-03). The IWDG
keeps running in Stop mode unless the `IWDG_STOP` option bit is cleared. The
task feeds it every 8 s, which wakes a chip that is in Stop mode.

## Supply voltage

Everything on the board runs from one 3.0 V rail. Its regulator (U3, an
MCP1703A) takes its input from a net that USB VBUS, the aux power header and
the coin cell share. Nothing on the board measures that input. The chip only
sees the rail, which is its VDD, VDDA and VBAT.

- On USB or aux power the rail is regulated. It says nothing about the
  source until the source is almost gone.
- A coin cell is at or below 3 V, so the regulator cannot regulate and passes
  the cell through, and the rail follows the cell. This is read from the
  schematic and the regulator's datasheet. It has not been measured.

`firmware/src/supply.rs` runs the chip's programmable voltage detector (PVD)
on the rail. The detector raises an interrupt when VDD falls below 2.64 V
(level 4, 2.59 V to 2.69 V), which is just under the 2.7 V that the
capacitance sensor needs. The metrics export the outcome as
`sensor_board_battery_low`.

- The metric goes from 0 to 1 and stays there until the board restarts. A
  coin cell sags while the radio transmits and recovers afterwards, and the
  metrics are rendered before a push is sent. The detector's output at that
  moment would miss the sag.
- The interrupt handler masks the detector's EXTI line (16) and leaves it
  masked. The masked line is the record that the detector tripped, which is
  also how embassy's EXTI code records an event. It keeps a supply that
  hovers at the threshold from interrupting again.
- The handler clears the line's pending bit, because a pending EXTI line
  keeps the chip out of Stop mode (RM0434).
- The interrupt reaches CPU1 without more setup. `PVDIM` in `SYSCFG_IMR2` is
  0 after a reset, which forwards it.
- The detector takes about 1 µA (datasheet).

Not tested on a board: any of it. In particular, it is not known whether a
fresh coin cell stays above the threshold while the radio transmits. If it
does not, lower `LEVEL` in `supply.rs`.

## The capacitance sensor

The chip is an FDC2214 (U9), which gives a 28-bit result. The schematic
says it is an FDC2114, the 12-bit version with the same pins, but U9 isn't
in the assembly BOM, and the boards have an FDC2214 on them. The datasheet
for both is `doc/fdc2114.pdf`. `firmware/src/sensor/capacitance.rs`
describes each channel's tank circuit and how a reading is converted to pF.
The firmware reports pF everywhere: in `protocol::Capacitance`, and as
`sensor_board_capacitance_farads` in the metrics.

- CLKIN is connected to ground, so the reference clock is the chip's
  internal oscillator. The datasheet gives 43.4 MHz as typical, and
  anywhere from 35 to 55 MHz. The firmware assumes 43.4 MHz. The
  capacitance is proportional to the inverse square of the clock
  frequency, so the values from a board can be off by tens of pF. Changes
  in the value on one channel are more accurate than the value itself.
- The firmware checks the device ID, which is 0x3055 for the FDC2214. On a
  board with an FDC2114, every reading would fail with "not initialized".
- Before 2026-10-18, the driver left the clock dividers at their reset
  value of 0, which is reserved, and read the result without waiting for a
  conversion to finish. Its raw readings (`sensor_board_capacitance`) had
  no defined scale. On board 4C0045 they were about 28,000,000 to
  29,000,000. If the chip treated the reserved dividers as 1, that's 31 to
  35 pF.
- The chip is in sleep mode between readings. A reading takes about 5 ms.

Not tested on a board: any of it. The drive current (`IDRIVE`) is the value
from TI's example, which uses the same tank circuit. The oscillation
amplitude should be 1.2 to 1.8 V peak, and it hasn't been measured with an
electrode attached.

## The motion sensor

The motion sensor is an EKMB130711, a passive infrared sensor whose output
goes high while it detects motion. It's on PA2. `firmware/src/sensor/motion.rs`
waits for the output with an interrupt instead of polling it, so a board on
battery stays in Stop mode until there is motion. `motion_enabled` in
`BoardConfig` turns it on (`config set --motion-sensor true`). It is not in
`Sensor`, because it has no poll interval.

- A detection starts when the output goes high, and ends once the output has
  stayed low for 20 s (`HOLD`). Motion that goes on, or comes back
  within the 20 s, is one detection. It was a minute until 2026-10-24.
- The metrics export `sensor_board_motion`, which is 1 during a detection,
  and `sensor_board_motion_detections_total`. The Pushgateway only keeps the
  last value pushed, so a detection that started and ended between two
  scrapes of it would be missing from the gauge. Use the counter
  (`increase(...)`) to count detections.
- A board on battery pushes when a detection starts and when it ends, as
  well as after every sensor read. A board on aux power records the change
  for its next scrape.
- The output goes high with each movement and low in between, even while
  someone is in front of the sensor. The hold bridges those gaps, so a
  person at a desk next to the board keeps a detection going for as long as
  they're there. That's what Home Assistant expects of a motion sensor.
- The sensor's output is undefined for 10 s after power-up (the datasheet's
  `Twu`), so the task waits that long before it watches the pin. After
  that, it treats the start like the end of a detection: it publishes
  "motion" at the first rising edge, but "no motion" only once the output
  has stayed low for a whole hold. A restart in front of someone used to
  report "no motion" for a few seconds (seen on 4D0021 on 2026-10-24),
  because the output happened to be low at the end of the warm-up.
- Reading the chip over SWD makes the sensor trigger. On 2026-10-24, with
  the sensor covered and `probe-rs read` polling PA2 every half second, its
  output went high every second or two, and the detection never ended. It
  ended 20 s after the reads stopped. A probe that is connected and not
  used does no harm. The datasheet asks for a stable supply with a
  capacitor at the sensor's power pin. The nearest one on the 3 V rail is
  C21 (0.1 µF), 7.8 mm from U10.
- R17 (100 kΩ) pulls the pin down, so it stays low on a board without the
  sensor, and the firmware doesn't turn on the chip's own pull-down. R17
  draws 30 µA while the output is high.

### Home Assistant

A board whose configuration has a Home Assistant server
(`config set --home-assistant '[address]:8123'`) reports every change of
the gauge to it, in both power modes. It sends `POST
/api/webhook/sensor-board-<serial>` with `{"motion":true}` or
`{"motion":false}`. The webhook ID comes from the serial number, so the
configuration only holds the address. Home Assistant runs on cerberus, next to
the border router, and the firewall there trusts the Thread interface, so a
board reaches port 8123 directly.

- The report goes out before the sensor reads and the push, because an
  automation may be waiting for it.
- A failed report is tried again until Home Assistant takes it: after 5 s
  the first time, and after a minute from then on. Otherwise a lost "clear"
  would leave Home Assistant showing motion until the next detection. Home
  Assistant answers 200 even for a webhook it doesn't know, so a wrong
  webhook ID shows up only as a missing entity.
- The first exchange after hours without one sometimes failed, and one a
  few seconds later succeeded. On 2026-10-26, 4D0021's first report after
  nine quiet hours failed, the push right after it succeeded, and the retry
  a minute later got the report through. The metrics count failed reports
  and pushes by their cause (`sensor_board_report_failures_total` and
  `sensor_board_push_failures_total`, with an `error` label), so that a
  board on battery shows why without a probe. The next failure was
  `out_of_sequence`: the Thread service still had a connection recorded,
  and refused the connect (see "Things learned about the TCP API"). A
  connect now aborts such a leftover. The short first retry stays, for
  failures with other causes.
- After a configuration change, the board reports the current state. After
  a restart, it reports at the first motion, or after 20 s without any.

Each board needs a trigger-based template binary sensor in Home Assistant's
`configuration.yaml`, which keeps its state across Home Assistant restarts:

```yaml
template:
  - triggers:
      - trigger: webhook
        webhook_id: sensor-board-4D0021000350475532303120
        allowed_methods: [POST]
        local_only: true
    binary_sensor:
      - name: Sensor board 4D0021 motion
        unique_id: sensor_board_4D0021_motion
        device_class: motion
        state: "{{ trigger.json.motion }}"
```

`local_only` accepts the boards, because Home Assistant counts the `fd94:…`
ULA addresses as local.

With `home_assistant` in `BoardConfig`, the longest `ConfigMessage` is 265
bytes, so `MAX_DATAGRAM_LEN` in `thread/ot.rs` went from 256 to 320. A
firmware from before then drops a longer datagram, but a real configuration
is far shorter.

- A configuration that's the same as the stored one isn't stored again, so
  it doesn't make the board report. To make a board report, clear the
  address with `--home-assistant none` and set it again.
- A report that arrives before the webhook exists in Home Assistant is lost,
  because Home Assistant answers 200 anyway. The entity then stays unknown
  until the next change.

Tested on board 4D0021 on 2026-10-18, with Home Assistant 2026.10.1 on
cerberus: changes from the motion sensor reached the entity, and a report
made by setting the address arrived about 0.1 s after the `config set`
returned.

Tested on 4D0021 on 2026-10-25, on a coin cell, with the probe off and the
board in Stop mode (`sensor_board_stops` 1), after the fix to
`stop_wakeup_alarm` (see "Stop mode"): a wave set the entity to "on" within
the second, and it went "off" 20 s after the sensor's output had gone low.
Not tested: a report retried after a failure.

## CPU2: FUS and the Thread stack

ST's images are in STM32CubeWB, under
`Projects/STM32WB_Copro_Wireless_Binaries/STM32WB5x/`. The firmware and the
bindings in `firmware/src/thread/ffi.rs` are written against V1.24.0.

`coprocessor install` sends an image to the firmware, which writes it where
FUS looks for one: on the page boundary that makes the image end just below
the secure flash area. ST's release notes give the same address for each
image (0x080EE000 for FUS and 0x0808C000 for the Thread stack, on a 1 MB
part). FUS then installs the image, resetting the chip a few times, and
starts an installed stack by itself. FUS can only install an image while FUS
itself is running, not while a stack is.

A join stores the dataset in the stored-configuration page, between the
firmware and the staging area (`firmware/src/persistent_config.rs`,
0x0803F000), because CPU2 loses its own settings when it restarts. At
power-up, a board with a stored dataset passes it to the stack and rejoins
by itself.

Things learned the hard way:

- The ROM bootloader boots CPU2 for its own FUS commands, and a CPU1 reset
  does not restart CPU2. After a DFU `:leave`, the firmware therefore finds
  CPU2 still using the bootloader's mailbox pointers. It clears the
  bootloader's marker and does a full system reset first
  (`reset_if_launched_by_bootloader`).
- FUS sends its command responses to the mailbox that CPU2 booted with.
  Before the fix above, an upgrade looked hung although it had run.
- A wireless stack switches the 48 MHz clock off unless CPU1 holds hardware
  semaphore 5 (AN5289). On aux power the firmware takes the semaphore before
  C2BOOT and never releases it. On battery it leaves the semaphore to CPU2.
- With HSI16 off, `SHCI_C2_THREAD_Init` never returns.
- The Thread stack uses SRAM1 above 0x20024000, so CPU1's RAM is limited to
  144 KB.
- CPU2 needs the traces queue to be initialised. Something also has to drain
  its traces and acknowledge its OpenThread notifications.
- In stack v1.24 the OpenThread CLI runs on CPU1, not CPU2, and everything
  goes through the OT command channel (3). The CLI channel (5) still has to
  be received from and acknowledged. Otherwise `SHCI_C2_THREAD_Init` never
  returns.
- FUS resets CPU1 during an upgrade. While a FUS operation is marked as in
  progress (`fus_busy`), a watchdog reset does not count as a failed boot.
- FUS can report itself idle, with no error, while an install is still
  pending: it did so for 14 s in the middle of installing the Thread stack.
  The firmware therefore stores the pending FUS operation across resets, and
  treats a change in the versions that CPU2 reports as the end of the
  operation.
- If FUS is given a file that is not an image, or the FUS version that is
  already installed, it reports no error and does not reset. It just stays
  idle. The firmware concludes that nothing was installed only after a
  minute of that.
- After installing a stack, FUS starts it by itself on its last reset.
- CPU2 stays inside an OpenThread callback until its notification is
  acknowledged, and the data that the notification points to is only valid
  until then. So the message of a received UDP datagram has to be read before
  the acknowledgement. `ThreadNotifRx::receive_with` in embassy-stm32-wpan
  exists for this, and the calls made inside it block (`thread/ot.rs`). CPU2
  answers calls while a notification is outstanding. ST's own code never
  acknowledges a notification while a call is waiting for its answer, and
  neither does the Thread service.
- A UDP datagram sent to a multicast address is also delivered to the
  sender's own socket if `mMulticastLoop` is set. That is how a board that
  sends a discovery request receives it too, and replies to itself.

Not understood yet, seen on 2026-10-11: two boards stopped receiving and
sending on the radio, one and five minutes after they had come back from a
restart into an image that they had fetched from the CLI through the border
router. CPU2 still answered calls, so their neighbor and router tables could
be read. But every neighbor's age kept growing, a multicast that the board
sent was not delivered back to it (`network show` through the board listed
nothing, not even the board), and its registration ran out. CPU1 kept
running, so the watchdog did not reset the board. A restart brought each
board back. One of the two, while it still answered pings and scrapes, did
not answer UDP from outside the Thread network. It happened again that
night: board 4C0045 was last scraped six minutes after it had restarted
into an image from such a push, and was still silent the next morning. Scrapes from two machines at
once and discovery requests did not make a restarted board do it again. The
three boards that had been updated through a board that morning kept
working.

Seen again on 2026-10-18, on board 4C0045. It restarted into an image from
`just push` at 10:43, and Prometheus last scraped it at 11:06, 23 minutes
later. `network show` through the border router did not list it. A power
cycle brought it back at 11:22. Nothing was read from the board while it was
silent.

## Board discovery

`firmware/src/discovery.rs` replies to a `protocol::DiscoveryMessage::Request`
(UDP port 61623, which every board listens on) with the board's serial
number, RLOC16 and addresses. `network show` sends the request in one of two
ways:

- Through an attached board (`DiscoverBoards`). The board multicasts the
  request and forwards each reply to the host as the `BoardDiscovered` topic.
  It also receives its own request and replies to itself, which is how it
  gets into the list.
- Through a border router. The CLI reads the device list from the border
  router's REST API (`/node` and `/diagnostics`, `cli/src/border_router.rs`)
  and sends the request to each routable address itself. It also sends to
  the boards it finds over mDNS, which include those on battery.

Details:

- A board sends its reply to port 61623 at the address the request came
  from, not to the request's source port. The CLI therefore binds port 61623.
- The reply is built from the status and addresses that the Thread service
  last published (`thread::Monitor`). The service publishes both on every
  state-change notification.
- The discovery task starts before the Thread stack does, so it retries
  `listen` every two seconds until it succeeds.
- The link columns of `network show` come from the attached board's neighbor
  table, matched by RLOC16. Through a border router they come from the route
  data in its own diagnostics entry, which has a link quality per router and
  nothing else.
- A message starts with a key derived from the layout of `DiscoveryMessage`,
  which includes `Addresses`. Boards and CLIs on different sides of a layout
  change ignore each other.

Tested on a board on 2026-10-10: the board listing itself through USB, a
reply to a request from the CLI through the border router, the RLOC16 in the
reply changing when the board became a router, and the border router's link
quality for it. Only that one board had the firmware. Tested on 2026-10-11:
the replies of two other boards forwarded by the attached board, with the
link columns from its neighbor table.

## Metrics

`firmware/src/metrics.rs` polls the sensors that are enabled in the board's
configuration, each at its own interval, and exports the readings to
Prometheus. The power mode in the configuration selects how:

- `Aux`: the board serves a scrape endpoint at `/metrics` on TCP port 9469.
- `Battery`: the board pushes to its configured Pushgateway after every
  sensor read. It is also a sleepy end device (see "Boards on battery").
  Before it reads a sensor it waits for the network, for up to 30 s
  (`Tcp::ready`): until it has attached and has an address that the
  Pushgateway can answer to. A sensor is due as soon as the board starts,
  a few seconds before that.

A board without a configuration is taken to be on aux power. It reads no
sensors, so it serves only the firmware build and the scrape counter, and it
registers its endpoint like any other board on aux power.

The metric types come from tinymetrics, and the HTTP from nanofish. The
firmware uses Aspen's fork of tinymetrics (`glittershark/tinymetrics`,
branch `fixed`), which adds `FixedGauge`: a gauge that holds a fixed-point
number from the `fixed` crate. The temperature, humidity, sound and
capacitance gauges use it. tinymetrics' own `Gauge` holds an `f64`, and the
code that formats an `f64` took about 10 K of flash (measured on
2026-10-18).
`firmware/src/http.rs` runs nanofish on the Thread TCP connection: one
request and one response per connection. The handler for a scrape request is
`Scrape` in `metrics.rs`. To add a sensor, add it to `SENSORS` and to the
`match` in `Exporter::read`, and its metrics to `Metrics`, all in
`metrics.rs`.

A scrape gets the full text format. A push sends only the samples, each
family's preceded by its `# TYPE` line (`Detail::Samples` in `metrics.rs`),
which cuts a push from about 3 K to under 1 K. The type lines have to stay:
the Pushgateway (1.11.2) rejects an untyped metric when another group has
the same metric with a type. That was tested on 2026-10-18 on a local
Pushgateway. Without help lines, the Pushgateway takes the help text from
the other groups.

Things learned about nanofish (0.13):

- It copies a whole response into one buffer before it sends it, and reads a
  whole response before it returns the status. So the metrics text is
  limited to `MAX_BODY`. If the Pushgateway's response to a push is longer
  than `MAX_RESPONSE`, the push fails as malformed and its status is lost.
- A request gets no response, and the connection is closed, if it is longer
  than `MAX_REQUEST`, has more than 16 headers, or has a method that
  nanofish does not know.
- It reports every failure of the stream as the same error. `Stream` in
  `http.rs` keeps the `TcpError`, so that the log still shows it.
- It took 9.4 K of flash (measured on 2026-10-11), and 6 K of RAM in the
  metrics task for the request and response buffers.

TCP is OpenThread's own implementation, running on CPU2 (`otTcp*`, wrapped
in `thread/ot.rs`). The Thread service has one TCP endpoint, so the firmware
has one connection at a time. The rest of the firmware uses it through
`thread::Tcp`. CPU2 reports TCP events in callbacks, which arrive as
notifications.

Things learned about the TCP API:

- When a connection comes in, CPU2 asks in a callback whether to accept it,
  and into which endpoint. The return value is written where ST's handler
  writes it: over the notification's first argument, before the
  acknowledgement (`set_callback_result`). The endpoint is written through the
  pointer passed in the callback.
- `otTcpAbort` sends the disconnected callback from inside the call, and
  does not return until that notification is acknowledged. So
  `ot::tcp_abort` acknowledges notifications while the call is in progress.
  That is what `Ot_Cmd_TransferWithNotif` in ST's wrapper is for. So far no
  other call needs this.
- An endpoint that closed its side first stays in TIME-WAIT and accepts no
  connection until it is aborted. For that reason every exchange ends with
  `Tcp::close`.
- The Thread service can still have a connection recorded at the next
  connect, although the last exchange ended with `Tcp::close`. It refused
  the connect (`OutOfSequence`) until 2026-10-26, which failed the first
  report after hours of quiet on 4D0021. Most likely a callback for the
  aborted connection arrived after the abort and overwrote `Closed`, but
  which one isn't known. A connect now aborts the leftover first. Not
  tested on a board yet.
- CPU2 reads sent data from the send buffer until the peer has acknowledged
  all of it. The firmware passes its 4 K send buffer to the stack with
  `otTcpSendByReference`, and adds later data after it with
  `otTcpSendByExtension`. So `Tcp::send` returns as soon as the data is
  queued, and a whole push goes out without waiting for acknowledgements in
  between. Only a send that does not fit in the buffer waits, for the
  send-done callback. Before this, each 512-byte piece waited for its
  acknowledgement, about 200 ms on a sleepy board.
- If a type is missing from the bindings, regenerate them with
  `firmware/tools/gen-thread-bindings.sh`, then format them with the rest of
  the crate.
- `otIp6GetUnicastAddresses` returns a pointer into CPU2's own memory, which
  CPU1 can read. The firmware follows the list only while its pointers stay
  in RAM.
- The stack takes `otTcpConnect` before the board has attached, and the
  connection then times out. A push made 1.2 s after a start, 0.2 s before
  the board became a child, did that every time.
- The stack accepts a connection from a peer that the board cannot answer,
  and does not report that the handshake never completes (not within four
  minutes). The endpoint then refuses every other connection. So an `Accept`
  request aborts a connection that has been opening for longer than
  `TCP_TIMEOUT`. A machine on the LAN that connects from a global address is
  such a peer: the border router's network data only has a route to
  `fc00::/7`.

Tested on a board on 2026-10-10: initializing the endpoint and the listener,
listening, connections that are refused or never answered, aborting a
connection that is being opened, and switching between serving and pushing
when the configuration changes. Also tested that day, with the board on a
border router's network: a scrape with `curl` from a machine on the LAN,
answered in full (1528 bytes), on a board that had served a scrape before.
Tested on 2026-10-11: pushes that a Pushgateway on the LAN accepted, from a
board that was a router and from one that was a sleepy end device.

Those tests were made with the HTTP that `http.rs` implemented itself before
nanofish. Since then `http.rs` has only been tested on a PC, on 2026-10-11,
with a stand-in for `thread::Tcp` over a local socket: scrapes with curl and
Python, the largest metrics text, requests that get no response, and pushes
that a Pushgateway (1.11.4) accepted and rejected. Not tested on a board
since: a scrape.

## Service registration

A board that serves scrapes registers the endpoint with the SRP server of
its network, which runs on the border router (`Tcp::register`, called from
`metrics.rs`). The border router advertises a registered endpoint over mDNS
on the LAN: a `_prometheus-http._tcp` service named `sensor-board-<serial>`,
on a host of the same name that has the board's routable address. Prometheus
gets its targets from there. On cerberus that is
`nixos/modules/cerberus/prometheus-mdns-sd.nix` in the universe repository,
which writes what avahi sees to a `file_sd` file. A board that pushes
registers another service, for the CLI to find it by (see "Boards on
battery").

The SRP client is OpenThread's, on CPU2 (`otSrpClient*`, wrapped in
`thread/ot.rs`). The firmware gives it a host name and one service. The
client does the rest: it finds the server in the network data, registers the
addresses that are reachable from outside the Thread network, and renews the
registration. `network registration` prints the state that the Thread
service last published (`GetRegistration`).

Things learned about the SRP client:

- CPU2 keeps nothing across a reset. It makes a new SRP key every time it
  starts, and the board gets new mesh-local and routable addresses. The
  server reserves a name for the key that registered it. So after a reset it
  rejects the board (`RegistrationError::NameTaken`) until the previous
  registration has run out. For that reason the lease and the key lease of
  the scrape endpoint are both two minutes (`SCRAPE_SERVICE` in
  `metrics.rs`), and the client renews every minute. The client retries by
  itself, with a growing delay.
- The lease intervals have to be set on the client, not in the service. An
  update that only changes the host uses the client's intervals, which
  default to two hours and fourteen days.
- ST's build starts the client by itself once the network data has a server.
  Nothing has to call `otSrpClientStart` or enable auto-start.
- CPU2 keeps the `otSrpClientService` it is given, writes the service's
  state into it, and keeps reading the name strings (`SrpBuffer`). The
  firmware reads the state from there.
- After `otSrpClientSetCallback`, CPU2 reports the outcome of each update as
  a notification (`MSG_M0TOM4_SRP_CLIENT_CB`), with the `otError` as the
  first argument. None of the calls that the firmware makes runs the
  callback before it returns.
- `otSrpClientRemoveService` leaves the service with the client until the
  server has answered. `otSrpClientClearService` takes it back at once, so
  the firmware calls it before it changes the service.

Tested on a board on 2026-10-11, on the border router's network: the first
registration, the mDNS advertisement as seen from the border router's
machine and from another machine on the LAN, scrapes from the border
router's machine at the advertised address (2588 bytes), the registration
after a restart (108 s and 109 s, with `NameTaken` until then), the service
removed within ten seconds when the board switched to pushing and
registered again when it switched back, and scrapes answered again 16 s
after a connection attempt that the board could not answer. With the module
live on cerberus, Prometheus scraped the board it found this way, under the
board's serial number as the instance. Only that one board had the firmware.
Later that day a second board, which had no configuration, registered four
seconds after it started, and Prometheus scraped the firmware build and the
scrape counter from it.

## Board configuration

`protocol::BoardConfig` is stored in the stored-configuration page, after
the dataset (`firmware/src/persistent_config.rs`). The dataset record is at
the start of the page, where firmware from before 2026-10-07 wrote it and
still reads it. The configuration record is at offset 0x200: the postcard
encoding of `BoardConfig`, prefixed with a key derived from its layout.

`firmware/src/board_config.rs` serves the configuration. It runs inside the
coprocessor task because it writes flash. For a board that is not attached,
the attached board multicasts a request (`ConfigMessage`, UDP port 61622,
which every board listens on). The target board replies with the
configuration it then has stored, which after a `Set` shows whether it
stored the new one. The attached board resends the request every five
seconds, and gives up after fourteen: a board on battery only gets the
request at its next poll, up to ten seconds later.

The `config` commands take the board's serial number in `--board`, whether
the board is attached or not (`route` in `cli/src/config.rs`). An attached
board is asked over USB, and any other board through an attached board that
is on a network. Without such a board, or with `--border-router`, the CLI
sends the request itself (`Devices`): from UDP port 61622, to the routable
address of every device that the border router's REST API lists and of
every board it finds over mDNS, with the same two times. The firmware has nothing for this. A board replies to port
61622 at whatever address a request came from.

- Changing `BoardConfig` (a new sensor, a new field) changes both keys: the
  one in flash and the one that `ConfigMessage` starts with. Boards on
  different sides of the change ignore each other's requests instead of
  misreading them. A board can only read a stored configuration in an older
  layout if `BoardConfig::decode` still knows that layout. It knows the one
  from before `sound_duration` (2026-10-18) and converts it with a 1 s sound
  duration. Without such a conversion, a board has no configuration after
  the update until it is set again, and a board on battery then acts as
  one on aux power.
- Writing either record erases the page and writes both records again, with
  no other CPU1 code running in between (`RadioFlash::rewrite_page`). This
  matters because the Thread service reads the dataset from flash to tell
  whether the board has a network. A reset during the rewrite loses both
  records.
- When the dataset is written, a configuration record that the firmware
  cannot decode is copied over unchanged.
- The metrics and `power.rs` use the configuration. Each has
  its own `Monitor` (`board_config.rs`), which notifies it of a change. The
  Thread service is given the power mode that the board started with.
- A request goes to the realm-local all-Thread-nodes address, so that it
  also reaches a board on battery (see "Boards on battery").

Tested on boards on 2026-10-07: setting a configuration over USB, and on
another board through the attached one. Both configurations survived a
firmware update, and the attached board's survived leaving its network and
joining it again.
Tested on 2026-10-11, through the border router: reading the
configurations of five boards, and changing one on an attached board, as
seen over USB. Also that day: reading the configuration of a board that is
not attached, named with `--board`, through an attached one. Not tested: the
commands with no board attached.

## Boards on battery

A board whose power mode is `Battery` is never on USB. JP2 connects its cell
straight to the 3 V rail, and USB power on top of that would destroy the
board (see `TODO.org`). So the firmware treats such a board differently in
several ways, and it has to be configured and updated over the network.

### No USB

`power.rs` reads the power mode once, when the board starts. A board on
battery does not start the USB device or the RPC server (`main.rs`). When
the power mode changes later, the board restarts after two seconds, which
leaves time for the reply to the request that changed it. So a `config set`
that makes a board a board on battery takes it off USB. The restart also
ends an update that is still on trial: the bootloader swaps the older
firmware back.

There are two ways back to USB. Both make the board a board on aux power:

- `config set --power-mode aux` over the network.
- Holding the button for five seconds (`button.rs`). That erases the
  configuration and keeps the dataset, so the board stays on its network.
  The LED blinks fast five times to confirm.

### A sleepy end device

`device_mode` in `firmware/src/thread/mod.rs` maps the configuration to a
`protocol::DeviceMode`. The Thread service switches to it before the board
first attaches. `network mode` prints the mode the service last switched to
(`GetDeviceMode`), for a board that is on USB.

- Aux power, or no configuration: a full Thread device, as before.
- Battery: a sleepy end device. Its receiver is off, and its parent keeps
  the messages for it. It polls its parent every 10 s
  (`protocol::SLEEPY_POLL_PERIOD`), whatever the intervals of its sensors.
  That bounds how long a request to it waits at its parent.

A sleepy board polls every 100 ms while it has a TCP connection, and for two
seconds after it sends a UDP datagram (`update_poll_period`). An answer
reaches the parent after the board has stopped listening. Without the fast
polls it would wait there until the next poll, and a push would time out.

For a sleepy board the firmware also sends `SHCI_C2_RADIO_AllowLowPower`, as
ST's sleepy end device example does. CPU2 accepts it. What it saves has not
been measured.

### Reaching it

- The requests that a board multicasts (configuration, discovery, update
  offers) go to the realm-local all-Thread-nodes address
  (`broadcast_address` in `thread/mod.rs`). A parent forwards that address
  to its sleepy children. It does not forward `ff03::1`.
- Everything that waits for a reply allows for the poll period: the board
  that relays a configuration request, the CLI's own requests through a
  border router, and the CLI's timeout for a call to a board.
- `firmware push` through an attached board learns the build of a board on
  battery as it does for any other board: from the board's reply to the
  offer, which takes up to a poll period.
- A fetch needs no change of mode. The board polls fast for two seconds
  after every chunk request, which carries the whole fetch.
- `network show` through an attached board collects replies for three
  seconds. A board on battery can take ten to reply, so it is often missing
  from that list. Through the border router, `network show` waits a poll
  period for the boards that are advertised as on battery (see below).

### Finding it without an attached board

The border router's `/diagnostics` has an entry for each router. A child is
only in its parent's child table there, without its addresses. So the CLI
cannot learn the address of a board on battery from the border router.

A board on battery therefore registers a service with the SRP server, as a
board on aux power registers its scrape endpoint (see "Service
registration"): `_sensor-board._udp` (`protocol::BOARD_SERVICE`), on the
configuration port. With `--border-router`, or with no board attached, the
CLI sends to the devices that the border router lists and to every board it
finds over mDNS (`targets` in `cli/src/border_router.rs`, `cli/src/mdns.rs`).
It finds them with `avahi-browse`, so it needs avahi.

- The service's lease is an hour, because every renewal costs the battery
  an exchange with the border router, and a signature on CPU2.
- With a long lease the name has to differ at every start
  (`SrpName::BoardAndStart`): `sensor-board-<serial>-<number>`, where the
  number is the end of the board's mesh-local address, which CPU2 makes up
  when it starts. With the board's name alone, the registration from before
  a restart blocks the new one for the whole lease, and longer: the client
  waits longer after every rejection. A board on battery that was off USB
  could not be found for that time.
- The registrations from before a restart stay for up to an hour, with
  addresses that the board no longer has. The CLI sends to those too, and
  gets no answer from them.

### Stop mode

Not solved yet, seen twice on 2026-10-11: a board that stopped hung when it
was to write its flash, and the watchdog reset it about 30 s later with
nothing written. Holding the button did that, and then a `config set`
through the border router (no reply, the old configuration still stored).
The board had been power-cycled with the probe taken off, and had a
multimeter in its supply lead. Reading the configuration and pushing
worked, for nine hours that night. If this happens on every write, such a
board cannot be configured, reset with the button or updated, and an update
would hang it at every attempt: three in a row put it in the ROM
bootloader.

It did not happen again on 2026-10-12, with the probe connected and not
used: 17 `config set` through the border router were all stored and
answered, ten of them while discovery requests kept arriving. The board
stopped for real meanwhile: in a temporary build that counted them, 33 of
its first 1124 wake-ups found HSE turned off. So it is not every write on a
board that stops. What differed on the 11th is the probe being off the
board, and perhaps the meter. One suspect in the code: `guarded` in
`radio_flash.rs` waits in a loop for CPU2 to end its suspension of flash
operations (`PESD`), and while it does, nothing acknowledges CPU2's
notifications.

To give a board back a disabled debug port without a power cycle, a
temporary build entered Standby mode at the start of `main` (CPU2 not yet
booted and allowed Shutdown, `DBGMCU_CR` cleared, the independent watchdog
started to reset the chip out of it). Standby powers the core down, and the
board came back with `C_DEBUGEN` clear.

A board on battery puts the chip in Stop mode whenever every task waits and
no peripheral is busy. The executor is embassy-stm32's (the `low-power`
feature), which does this by itself: it pauses the time driver, has the RTC
wake the chip for the next timer, and enters Stop 1. `power.rs` decides
whether a board stops (`stops`). On a board that does not, its task holds a
guard that keeps the executor from stopping. The metrics export the decision
as `sensor_board_stops`, so that a board on battery shows whether it stops
without a probe, which would change the answer.

- The chip wakes for a timer (through the RTC), for a message from CPU2
  (the IPCC), and for the button. CPU2 stops and wakes by itself for its
  data polls. In the log of a board that polled every 10 s, CPU1 woke at
  each poll too.
- A measurement with the microphone keeps the chip awake: the DMA ring
  buffer holds a guard for as long as it exists, which is why the driver
  only creates it for the measurement (`Capture` in `pdm.rs`).
- CPU1 sets how deep CPU2 may let the chip sleep (`allow_cpu2_low_power`),
  before CPU2 boots. At reset that is Stop 0.
- The two cores share the clocks, and ST's applications have a protocol for
  changing them around a stop (`EnterLowPower` and `ExitLowPower` in
  `stm32_lpm_if.c` of STM32CubeWB), which CPU2 follows too. A core that
  stops takes hardware semaphore 3, and switches the system clock to HSI16
  if the other core has stopped already. If the other core still runs, it
  keeps semaphore 4 instead, and the other core switches when it stops.
  After a stop the system clock is HSI16, and HSE and the PLLs are off. The
  core that wakes first turns HSE on again.
- A board whose debug port is enabled does not stop (`C_DEBUGEN`, which the
  firmware reads at start). A probe cannot read the memory of a chip that
  stops and starts, and the log goes through that. With a session attached
  to a board that stopped, probe-rs reported a corrupted RTT control block
  and a locked-up core, and the board's pushes failed. The flag survives a
  reset, and probe-rs leaves it set: it was still set after sessions that
  were killed, after a `probe-rs read` that exited by itself, and after
  `probe-rs write` had written it to 0. So a board that a probe has touched
  only stops again after it has lost power.
- A board that stops also turns off the debug clocks in sleep
  (`enable_debug_during_sleep`), which cost most of what stopping saves.
  `probe-rs attach` to such a board still read its log buffer, in pieces.

embassy-stm32 0.6.0 needs the fixes on the fork's `wb55-stop` branch for
this. Each of these kept the firmware from working with Stop mode:

- The stop sequence used the wrong semaphores. ST numbers them from 0, as
  the registers are numbered, and the driver's channels start at 1, so
  `get_hsem(3)` and `get_hsem(4)` were HSEM_R2 and HSEM_R3. HSEM_R2 is the
  one that guards flash operations (`radio_flash.rs`).
- It released semaphore 4 before the chip stopped. ST's sequence keeps it
  until the core wakes.
- Nothing restored the clocks after a stop. The fix turns on what was on
  before (HSE, the PLLs, MSI) and switches the system clock back, under
  semaphore 3. It does not use embassy's full clock setup, which goes
  through MSI at 4 MHz: CPU2 is clocked from the system clock too. Without
  the restore, a measurement after the first stop waited for samples
  forever, because PLLSAI1 was off.
- `IpccRxChannel::receive` held a guard while it waited for CPU2. The
  firmware always waits for CPU2 on several channels, so it never stopped.
- When the next timer was too close to pause the time driver, the executor
  entered Stop mode anyway. Time then stood still, and the watchdog reset
  the board.
- The chip's stop flags were never cleared.
- It turned the SMPS off before every stop, and never on again (see "The
  SMPS").
- When it resumed time after a stop, it cleared the RTC's line in EXTI's
  pending register with a read-modify-write (`stop_wakeup_alarm` in
  `rtc/low_power.rs`). The register is write-1-to-clear, so that cleared
  every pending line, before the EXTI interrupt ran. A GPIO edge that woke
  the chip was lost: the interrupt ran and found nothing pending, or never
  happened. The motion sensor's detections then didn't start, or never
  ended. The button's line and the supply monitor's had the same problem.
  Found on 2026-10-25, with a temporary build that pushed the EXTI registers
  every 10 s. embassy's main branch still has it, as of 2026-02-28.

embassy's main branch, read on 2026-10-11, no longer stops with the time
driver running. The others are still as in 0.6.0. The `wb55-stop` branch
starts from the release, because the fork with the Thread support uses
released crates.

The firmware image grew by 10.9 K with this, to 209,280 bytes. With the
HTTP crate and the supply monitor merged in, it is 219,736 bytes, which
leaves 9.6 K.

### The SMPS

The chip has a step-down converter that can feed its core and its radio
from the 3 V rail in place of the linear regulator, at about half the
current. The board has the parts for it: L1 (10 nH) and L2 (10 µH) between
VLXSMPS and VFBSMPS. A board on battery starts it (`start_smps` in
`main.rs`), as ST's applications do: output 1.40 V, corrected by the chip's
production calibration, and 80 mA at its start.

- It switches at 4 MHz, which is what 10 µH is for (AN5246; 8 MHz wants
  2.2 µH). Its clock is set to HSI16 / 4. The status field read HSE as the
  source in use all the same, and HSE / 8 is 4 MHz too.
- At 1.40 V the radio sends with at most 3.7 dBm (ST's `app_entry.c`).
- In Stop 1 and Stop 2 the chip takes the converter out of the circuit by
  itself and puts it back afterwards. ST's stop sequence does not touch it.
  embassy-stm32 turned it off before every stop and left it off. The fork
  no longer does.
- Nothing switches it to bypass when the supply gets low. That takes a
  higher brown-out level, which is an option byte.
- Boards on aux power do not start it yet. It has only been tried on one
  board.
- Erratum 2.2.21 in ES0394 (`doc/es0394.pdf`): "In Stop 2 mode and Stop 1
  mode, during the switching between SMPS and SMPS bypass modes, the SMPS
  may generate an unstable situation that may cause interruption of the
  full system." The workaround is to use the SMPS only with Stop 0, or not
  at all. It applies to silicon revision Y (`REV_ID` 0x2001 in
  `DBGMCU_IDCODE`), not to revision X. Board 4D0021 is revision Y (read on
  2026-10-25), so the boards very likely are. The firmware doesn't follow
  the workaround yet, and no failure has been traced to it.

Tested on board 4B002E on 2026-10-12, at 3.0 V: `PWR_SR2` showed the
converter in step-down mode after the start, and still at a push on a board
that stopped in between. Pushes were accepted throughout. Turning it off
and on through the probe, twice, made no difference to the sound level that
the board measured (61 dB SPL either way). Not measured: what it does to
the current.

### The current

Aspen measured it on 2026-10-11 with a multimeter in the positive lead, on
its mA range, on board 4B002E at 3.0 V after a power cycle with the probe
taken off (sound every 10 s, a push after each measurement):

- About 0.02 mA while the chip is stopped.
- 6 to 10 mA for about two seconds, every ten seconds: one second of
  measuring sound, then the push, which takes a bit more than a second with
  the board polling its parent every 100 ms.

Measured again on 2026-10-18, on the same board with the SMPS on: 0.02 to
0.06 mA while stopped, and 5.5 to 6 mA while measuring and pushing.

So what a board on battery draws is set by how often it measures and
pushes: about 2 mA on average with this configuration. What would bring
that down: a longer interval, and a push that takes less time on the air.
The SMPS, which was off for this measurement, should lower the current
while the chip runs. The 20 µA only matter once a board measures every few
minutes. A current of several milliamps for seconds is also a lot for a
coin cell.

Timed on 2026-10-18 on board 4B002E, with a probe attached and the board
not stopping, from the start of a sound measurement to the response to the
push:

- Before: 2.4 s. The measurement took 1.1 s (1 s, plus 100 ms for the
  microphone to settle). The push took 1.3 s, almost all of it spent
  sending 3 K of text in 512-byte pieces, each waiting about 200 ms for its
  acknowledgement.
- After: 0.57 s. The measurement takes 226 ms with `config set
  --sound-duration 125ms`. The push takes 0.35 s: it sends 0.6 to 0.8 K
  without help lines, queued at once, and the response comes back about
  300 ms after the request is queued.

### Not done

- The chip only reaches Stop 1. embassy-stm32 keeps Stop 2 for when the
  IPCC, I2C1 and the DMA controllers are not in use at all.
- The sensors are not put in a low-power state when they are not polled.
  Only the microphone is: it powers down when its clock stops.
- After three failed boots in a row a board enters the ROM bootloader (see
  "Logs and panics"). A board on battery cannot be reached there, and stays
  in it until its cell is taken out.

### Things learned

- ST's FTD image can be a sleepy end device and a CSL receiver. Its build
  sets `OPENTHREAD_CONFIG_MAC_CSL_RECEIVER_ENABLE`
  (`openthread_api_config_ftd.h` in stm32-mw-wpan). The MTD image is not
  needed.
- `otThreadSetLinkMode` on an attached board makes the stack detach and
  attach again by itself, if the change needs that. The board was a sleepy
  child again within ten seconds of a change to battery, and a router again
  about a minute after a change to aux.
- The stack's data poll period is the shorter of the period it is given and
  the child timeout less four seconds (from the stack's source). The
  firmware's 10 s is far below the default child timeout of 240 s. A poll
  period above that would also need a longer child timeout, which the stack
  limits to eight hours.
- A multicast to `ff03::1` does not reach a sleepy child. A parent forwards
  only the groups that the child registered with it, and the link-local and
  realm-local all-Thread-nodes addresses (`mesh_forwarder_ftd.cpp` in the
  stack's source). Every Thread device is subscribed to those two, so
  boards on a firmware from before this change get the requests too. So do
  the other sleepy devices on the network, which have to receive and drop
  them.
- `otThreadGetRealmLocalAllThreadNodesMulticastAddress` returns a pointer
  into CPU2's memory, like `otIp6GetUnicastAddresses`.
- The firmware does not use CSL, which would make the board a synchronized
  sleepy end device. It was tried on 2026-10-11 with a CSL period of 10 s
  (`otLinkSetCslPeriod`, in microseconds, a multiple of 160). With the
  board silent (no Pushgateway), pings from the border router's machine
  arrived in batches 10 s apart, but with stretches of 30 to 60 s in which
  none arrived. That happened with a sensor board as the parent and with
  the border router, and with the radio's low-power mode allowed or not. A
  message that misses its windows waits for the next data poll, and with a
  CSL period set the stack only polls every 99 s by itself. A CSL window is
  also at least 6 ms of receiving (the stack's minimums). Polling every
  10 s delivered every ping within 11 s.
- A change of the configuration that makes the board attach again can delay
  the reply to the request that made it: a `config set` from aux to battery
  through another board was answered after 13 s.

### Tested

All of this was on 2026-10-11, on board 4B002E (battery, sound every 10 s, a
Pushgateway on the LAN), with a sensor board and with the border router as
its parent. The board ran from USB power throughout, also while its firmware
was off USB.

- The board attaching as a sleepy child, which the border router's
  diagnostics show as receiver off, and pushes that the Pushgateway
  accepted, about one every 10 s.
- With the sound sensor at 30 s, a data poll every 10 s: 45 of 45 pings,
  one a second, came back in batches 8 to 11 s apart.
- Requests sent to the all-Thread-nodes address were answered by two boards
  on the firmware from before that change.
- Through the board, attached and on aux power, to board 4C0045, which was
  configured as on battery for the test and had the border router as its
  parent: the `config set` that made it sleepy, seven `config show`
  (answered after about 9 s when the board had been idle, and within a
  second right after another request), `network show`, which listed it, and
  the `config set` back to aux.
- `firmware push` through the board to the two other boards, which were on
  aux power and on the firmware from before this work: both fetched the
  image and reported the new build.
- The registration of the board service, its advertisement over mDNS, and
  `config show` and `network show` through the border router, which found
  the board that way.
- Erasing the configuration, with a temporary timer in place of the button:
  the board kept its network, and was a full Thread device afterwards.
- The button, which Aspen held while the board was on battery and off USB:
  the LED blinked fast, and the board came back on USB without a
  configuration, on its network, as a full Thread device with its scrape
  endpoint registered.
- Off USB: the board left USB two seconds after a `config set` to battery,
  pushed to the Pushgateway, registered under a new name five seconds after
  the restart, answered a `config show` through the border router after 3 s,
  and came back on USB after a `config set --power-mode aux` through the
  border router, which it answered.
- `just push` with no board attached, while the board was off USB: the CLI
  offered an image of 198,352 bytes to five addresses (the two other boards
  from the border router's list, and this board's registrations over mDNS).
  All three boards fetched it in about three minutes and restarted. The
  board on battery then pushed its metrics as the new build, registered
  under a new name, and answered a `config show` through the border router.
- `network show` through the border router, after it was made to wait for
  the boards on battery: it listed all three boards, three times out of
  three.

Stop mode was tested later that day on the same board, powered at 3.0 V
through the aux power connector, with JP2 open, USB unplugged and the probe
connected. The board could not be power-cycled, so its debug port was
enabled throughout, and the builds that stopped were temporary ones that
ignored that.

- With the debug clocks left on in Stop mode and no probe session: 14
  pushes that the Pushgateway accepted, one every 10 s, each with a sound
  measurement.
- With the debug clocks off, the PLL off and HSI48 left to CPU2, as a board
  on battery now runs: 17 pushes in 215 s, and a `config show` through the
  border router.
- `just push` with no board attached, while the board stopped: it and the
  two boards on aux power fetched an image of 209,280 bytes and restarted
  into it. The board then pushed as the new build, and the other two served
  scrapes as the new build.
- The same build on aux power, on the same board: a router, with a scrape
  that included a sound level.
- The build that honours the debug port: under `cargo run` the board logged
  that it does not stop, and its pushes were accepted.
- The same build after a power cycle with the probe taken off: the board
  stopped by itself (see "The current"), and the Pushgateway accepted its
  pushes meanwhile.

Tested on 2026-10-12, on the same board: with the wait for the network, no
push failed after a start (four pushes accepted in the first 45 s, where
the first used to time out and the next came a minute later).

Not tested: a board that runs from a cell, a board with I2C sensors that
